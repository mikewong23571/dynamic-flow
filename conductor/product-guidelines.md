# 产品与前端设计指南

## 设计目标

遵循 [当前设计](../docs/design.md)：画布是主要编辑入口，节点、连接与配置共同表达流程；画布与 Agent 修改同一份 IR。JS 仅供按需只读查看，不要求用户编辑代码。

### 当前视觉结论（2026-09-20）

用户明确否定了组件 Spike 的组件呈现、样式和色彩，认为效果廉价。该 example 只保留接入验证价值，不作为正式产品的视觉或交互模板。此前浏览器检查通过不代表用户认可设计。

正式实现前，先用真实任务完成一个代表性工作区：查看问题样本 → 针对上下文提出修改 → 比较候选 → 分别采用方法和产物。主工作内容与辅助对话保留共同上下文，避免直接沿用实验中按组件种类拆分的三个 Tab。

先研究具体成熟界面，确定一种主要设计方向，实际呈现后讨论，再扩展其他页面。不能只列参考品牌、换主题色或堆叠组件默认样式。设计评估独立于类型检查、构建和交互测试。

本次明确需要纠正：无任务价值的口号与装饰编号；大片留白搭配过小过淡正文；整页灰绿染色却缺少状态区分；默认树、表格、JSON、编辑器视觉各自为政；为展示库能力而安排布局。

现代、功能完整、有统一设计判断的工作台。用户依靠布局、控件、状态与真实内容理解产品，不需要阅读成片说明才能操作。原型可以小，但界面应从头到尾一致。

不把品味等同于某种灰色主题、极简样式或现成模板。允许有表现力的颜色、动效和构图；每项选择都要与任务、信息层级和整体方向一致。

## 参考方式

实施前查看真实产品界面、官方控件示例及交互规范，不能只写“参考 Linear”。本次已阅读以下官方资料，后续具体页面仍需实看和操作：

- [Linear 界面演进](https://linear.app/now/behind-the-latest-design-refresh)：学习布局位置的一致性、信息密度、视觉主次。
- [Primer](https://primer.style/product/)：学习控件语义、视觉变量、操作模式与状态。
- [Primer Button](https://primer.style/product/components/button/)：学习主次操作、尺寸和加载状态。
- [Primer 渐进展示](https://primer.style/product/ui-patterns/progressive-disclosure/)：按需要展开细节，不隐藏完成任务所需的信息。
- [VS Code UX](https://code.visualstudio.com/api/ux-guidelines/overview)：学习导航、主要工作区和辅助面板的职责。

为正在实现的页面保留少量参考及采用理由。借鉴行为和结构，结合本产品做设计；不拼贴多套视觉风格，不同时引入多套基础组件库。

## 先任务后布局

先确定用户正在查看的对象、当前状态、主要操作及操作后的反馈，再选择页面和控件。

- 查看运行：主要空间留给真实结果与进展。
- 检查结果：在保留上下文的同时查看输入、输出与执行记录。
- 试验改法：样本与 Current / Candidate 比较成为主工作区。
- 修改做法：在画布拖放节点、连接端口，在 Inspector 调整配置；也可以通过对话修改同一份定义。候选变化展示节点、连线与参数的变化。

画布保留流程上下文，Inspector、样本结果和对话面板按当前任务展开。列表用于材料、样本和运行记录，不替代流程画布。避免所有面板永远同时占满屏幕。

## 控件语义

| 意图 | 交互约定 |
| --- | --- |
| 切换工作或对象 | 导航列表、面包屑；存在真实层级时使用树 |
| 编辑流程 | 画布节点、具名端口连线与节点配置 |
| 同一对象不同内容页 | Tabs |
| 同一内容不同呈现方式 | 分段切换 |
| 执行动作 | 具有明确动词的按钮 |
| 多选样本 | 复选框及批量操作栏 |
| 查看当前对象详情 | Inspector 或内联展开 |
| 少量次要操作 | 操作菜单 |
| 小范围临时输入 | Popover 或 Dialog，按实际交互选择 |
| 比较候选结果 | 对齐的比较工作区 |

同一意图在全产品中保持一致。一次选择与“进入详情”应能区分；颜色标签不充当含义不明的按钮。

每个操作组具有明确主次。高频操作就近出现；低频操作可以收纳，但关键动作不能只依赖悬停才可发现。

## 文字与反馈

- 优先显示材料、结果、数量、状态和动作；不在每个区域放置功能介绍。
- 标签简洁明确，例如“已选 3 条”“试运行”“采用方法”“保留结果”。
- 关键差别必须清楚，如采用方法的影响范围、历史结果与重新对照运行的区别。
- 首次使用、错误原因和后续处理可提供必要帮助；不把必要标签全部替换成图标或 Tooltip。
- 界面用用户的工作语言；节点内部 ID、事件协议等实现细节放在按需查看的调试区域。
- 展示错误时给出可行的下一步，不只显示错误码。

## 视觉体系

在实现代表性页面时统一确定字体层级、间距、行高、控件尺寸、圆角、边框、图标、颜色语义和动效，并集中管理视觉变量。基础控件沿用 shadcn/ui；具体视觉方向须在代表性工作区验证，不沿用旧 Spike 的配色与布局。

选中、运行中、失败、完成和候选版本各有稳定表达；状态不能只靠颜色。内容保持主要视觉权重，导航和辅助信息支撑定位。

设计可读的信息密度，不堆叠大卡片，不把所有区域做成同等突出的模块。动效用于反馈和理解变化，避免干扰持续阅读。

## 完整状态与真实内容

检查空状态、加载、运行、部分完成、失败、长标题、长结果、多条记录，以及较窄桌面窗口。不能只验证理想状态的一张截图。

刷新和流式更新尽量保留选择、阅读位置和输入；切换试验模式后可以返回此前上下文。执行中应能看出确切状态，演示数据不能冒充真实运行。

## 易改的前端实现

- 一套基础组件；按实际复用需求抽取少量业务组件。
- 组件名对应用户可见功能，例如 WorkflowCanvas、NodeInspector、SampleBrowser、ResultComparison。
- 页面组合、业务状态与基础交互职责清楚，但不为每个组件建立多层抽象。
- 统一视觉变量，避免散落的特殊颜色、尺寸和页面级临时覆盖。
- 不建设仅为原型服务的通用页面 DSL 或自有设计系统框架。
- 控件候选及依赖关系见 [组件分析](./component-options.md)。

## 前端验收方式

先构建代表性的完整工作区，使用真实材料走完检查、试验、修改、采用。实际打开浏览器操作并检查截图，再扩展页面。

核验三个问题：用户能否看懂当前状态；关键操作能否直接完成；新增页面是否延续既有设计规则。自动测试通过不等于视觉与操作验收通过。
