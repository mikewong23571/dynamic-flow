# Dynamic Workflow Workbench

当前基线：2026-09-20，持续工作项 + 画布 + JS 语义子集 IR。完整设计以 [docs/design.md](../docs/design.md) 为准；[原稿 v2](<../docs/archive/Dynamic Workflow Workbench — 产品与技术设计 v2.md>) 只作历史参考。

## 产品定义

用户登记需要持续推进的业务工作项，提供目标、完成条件与独立证据，选择处理方法。Agent 形成节点工作流；用户通过画布和自然语言修改方法，通过正式执行取得进展、等待外部消息或到期、补充证据并继续同一件事。管理者观察阶段、依据、阻塞与下一触发，而不是以节点计数代替业务完成。

核心优先级：可用、用户友好、实现简单、容易指导改动、coding agent 容易修改。 当前只为承载用户故事编写直接功能，不以建立软件抽象为目标。通用机制复用现成组件，自研集中于业务定义与必要衔接。安全、权限、隔离、多租户和生产治理不在原型范围。

## 核心闭环

工作项与完成条件 → 选择方法 → 固定版本和独立输入 → 计算并记录里程碑 → 持久等待 / 事件或到期继续 → 补充证据 / 改进方法 → 确认依据后结项，必要时重开。

方法编辑闭环继续保留：生成 IR → 画布调整 → 样本试验 → 比较 → 独立采用定义/保留结果。试验不提交工作项业务进展。

人类无需编辑 JS。JS 可以只读查看；业务修改在画布、节点配置或 Assistant 中完成。列表用于材料/结果/执行实例，不作为流程画布的替代。

## 最少对象

| 对象              | 意义                                                                         |
| ----------------- | ---------------------------------------------------------------------------- |
| Work              | 方法工作区、标题、目标说明、样例材料与归档状态                               |
| WorkItem          | 稳定业务身份、目标、独立证据、阶段、完成条件与历史                           |
| DefinitionVersion | 一版固定的 IR 定义；候选为可编辑草稿                                         |
| Run               | 按固定定义和工作项输入修订执行；保存等待/事件/实例检查点，试验也复用同一模型 |
| NodeResult        | 节点实例的输入输出、状态及产物来源                                           |

Node / Edge 属于定义；运行实例关联稳定输入项 ID。反馈与修改说明附在草稿/运行上，不单建 Region、Site、Correction 或 Spike 平台。

## 关键约定

- IR 是受约束的 JS 语义子集；画布、Agent 与只读 JS 表示共享一份定义，runtime 执行其中明确的节点与连接语义。
- 不从任意源码还原工作图；不用 AST、行号或 source range 作为节点身份。
- 运行前固定 DefinitionVersion，编辑生成草稿，不修改正在执行的版本。
- 节点处理可调用 Pi 或普通 JS 函数；不重建 Agent loop。
- 语义包括 Agent/Function/Branch/Wait/Milestone、map/flatMap/aggregate、显式依赖和有限并发；普通连线不允许环。输入输出由 Ajv 实际校验，严格 reduce/filter 与完整端口类型推导未实现。
- 定义节点与执行实例分开，材料数量变化不要求复制整张图。
- 试运行先支持单节点与明确输入；结果比较绑定样本快照，草稿变化会使旧比较过期。
- 采用定义与保留结果独立；旧/新结果只有被显式选择为后续输入时才复用，并保留来源。
- 新输入续做发起新 Run；持久等待与中断后显式 resume 可继续同一 Run，保留已成功实例。不恢复任意调用栈，不承诺隐式缓存或外部副作用恰好一次。
- 里程碑仅在 workItem/full/commit 写业务进展，preview 与候选比较不写；Run 完成不自动结项。工作项未决运行期间禁止换方法或另起运行。
- Work、定义、结果和等待事件保存到方法目录；WorkItem 独立保存于 data/work-items。业务状态不依赖聊天记录或瞬时进程内存。

## 模型设置与工作库

模型设置（G1）已经接入正式客户端和后端。作者 Assistant 与工作流 Agent 节点共用当前配置；界面可设置协议、服务地址、模型名、API Key、推理强度、Temperature、Top P 和上下文窗口。

支持的公开协议值是 `anthropic-messages`、`openai-chat-completions` 与 `openai-responses`；任意端点指兼容所选协议的端点，不承诺兼容私有协议。后端映射各协议的实际参数，反馈支持的推理档位与限制；配置格式合法或保存成功不代表真实端点调用已通过。

尚未保存工作台配置时，后端从根目录 `.env.local` 与进程环境变量读取 `LLM_PROTOCOL`、`LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_KEY` 作为初始值，同名进程变量优先。界面保存至 `data/model-settings.json`，之后优先使用该文件，不改写环境文件。API Key 留空沿用现有值；读取配置和界面不会回显密钥，密钥不写入单个工作文件。配置失败、调用失败和参数不支持均明确报错，不使用假模型兜底。

工作库维护（G2）提供标题/目标搜索、分页、短标题修改、归档与恢复。标题和完整目标独立保存；Assistant 可以提供简短标题，但不覆盖用户已手工修改的标题。归档保留材料、定义及历史结果；原型不建设模板市场或跨项目发布。

## 生命周期场景与验收

当前验收基线为 [H1–H11 / L1–L5](../docs/workitem-stories.md)：一个 CVE 工作项取得调查进展后等待公告，跨进程重启继续，补充证据、使用新方法复核，按条件结项再重开；外部 HTTP 能取得相同业务状态。CVE 是示例，不内置分类结论。

原有十九个故事、G1/G2 与 T1–T8 继续回归。客户反馈分类与报告场景证明短流程可用，不能替代长生命周期验收。当前通过、失败与剩余项由 [本轮 track](./tracks/workitem-lifecycle_20260920/evidence.md) 汇总；这里不提前宣布全部验收通过。

用户应能全程操作界面，不需要编辑代码或手工改数据库。运行结果与定义版本、节点、输入项对应；重新打开后仍能查看。视觉方向需通过代表性页面讨论，技术检查不能代替设计验收。

## 明确移除

核心源码编辑/代码 Diff、通用程序分析器、任意 JS 与画布双向转换、源码位置索引、通用代码片段执行与恢复、生产级分布式调度/通用缓存/失效平台、IDE 式固定多栏、无需求的多包架构。

正式应用位于 src/，已实现独立工作项、共享 IR、画布编辑、有限并发节点运行、持久等待/里程碑、同样本比较、显式结果续做、Pi 接入与有限检查点恢复。默认 `pnpm dev`、`pnpm build`、`pnpm test` 与 `pnpm test:browser` 面向正式应用；历史组件实验使用 `pnpm spike:*`，其包接入证据不等于正式架构或视觉验收。

[伪代码 Spike](../spike/README.md) 保留需求拆分与测试推演。当前接口以 shared 类型和实际模块交接为准；[模块与验收地图](../docs/implementation-map.md) 分配 P01–P32、G1/G2 和 H1–H11 的职责。模块边界和字段仍可按具体反例修订，不能为了维护旧骨架削弱故事。
