# Dynamic Workflow Workbench

状态：原型产品基线。定位已经用户确认；组件选型另行讨论。

## 产品定义

一个面向长尾任务的可交互工作台。用户提供目标和材料，Agent 生成可阅读、可修改的程序来完成工作；用户能够看懂当前做法、查看实际结果、用真实材料试验局部改法，并保留有效成果继续工作。

原型充分复用现有开源组件，以简单、直接的代码实现完整体验，让用户能够理解实现、指导改动，也让 coding agent 容易定位和修改。

## 优先级

1. 可用：真正完成用户工作，打通操作与执行。
2. 用户友好：对象、状态和操作容易理解；界面有统一设计逻辑。
3. 实现简单：优先现成能力和直接组合，少量核心业务代码。
4. 易于修改：实现与产品概念对应，用户可以指导，coding agent 可以局部修改。

安全、权限、隔离、多租户及生产级治理不属于原型范围，不为这些目标增加组件、开发任务或验收门槛。

## 核心闭环

目标与材料 → 形成做法 → 真实运行 → 检查局部结果 → 真实样本试验 → 修改候选方法 → 比较 → 采用方法／保留产物 → 继续完成工作。

Visualize、Spike、Debug、Modify 都在原型范围。可以用简单交互实现，不能把其中某项永久推迟到通用运行框架完成以后。

## 核心对象

| 对象 | 对用户的意义 |
| --- | --- |
| Work | 正在完成的一件事情及其目标、材料 |
| MethodVersion | 一版具体做法及其真实执行程序 |
| Run | 按某版做法进行的一次执行 |
| Region / Site / Call | 工作阶段、程序位置、一次实际调用 |
| Artifact | 已产生、可以检查和继续使用的结果 |
| Spike | 用真实样本进行的一次局部试验 |
| Correction | 人的反馈、选择及原因 |

这些是业务概念，不要求每个对象都有独立页面或独立软件包。

## 产品约定

- 程序决定实际执行；工作地图由程序中的明确结构及运行事件生成。
- 运行状态来自实际执行，Agent 的解释不能代替执行事实。
- 执行绑定不可变 MethodVersion；候选修改不覆盖正在执行的版本。
- 采用新方法与保留某个结果是独立操作。
- Agent 会话帮助工作，Work 状态不能只保存在会话中。
- 可独立试验的局部具有明确入口和输入；复杂代码可以显示源码或扩大试验范围。
- 程序需要消费结构化结果时做局部验证，不建设统一业务 Schema 平台。
- 工作续做允许基于保留产物重新调用入口，不承诺恢复任意 JavaScript 调用栈。
- 反馈场景中，明细变更后可以直接重新汇总；不要求通用依赖失效引擎。

## 首个完整场景

用户提交客户反馈与背景资料，Agent 形成分析、归并、调查、建议的程序。用户先用少量反馈试验，正式运行后发现某条结果太泛，定位并修改做法，对同样样本比较，保留满意结果，用新方法重做和处理剩余反馈，最后生成建议。

先以 3 条真实样本打通完整闭环，再扩展到设计稿中的 50 条反馈与动态调查。反馈分析是首个验证场景，产品实现不能硬编码成只支持反馈分析的专用应用。

## 原型验收

- 用户能通过界面完成核心闭环，无需手工修改数据库或借助开发者执行隐藏步骤。
- 能区分当前方法、候选方法、历史运行和各自的结果。
- 能把旧版满意结果与新版结果组合起来继续工作，并查看来源。
- 重新打开应用后能看到目标、材料、方法、结果与修改记录。
- 用户能理解当前正在做什么、已选中什么，以及下一步如何操作。
- 实现能被用户和 coding agent 解释、定位和修改。

## 范围边界

不建设任意 JavaScript 与画布无损互转、通用 Workflow 治理平台、自动 Prompt 优化器、完整依赖分析器或新的 Agent Harness。
