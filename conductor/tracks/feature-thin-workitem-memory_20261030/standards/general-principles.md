## 0. 写代码前先定框架，再写业务

出处：go-backend-developer / python-backend-developer —— 两者共同的「Daedalus 前置规则」（SKILL.md §2.2.0 / §3.2.0）

> 以下规则不能等到 `code-compliance-check` 后置发现再改，因为可能引发接口、错误处理、安全、并发或资源管理重构。**必须在写代码时直接应用**。

- **结构与复杂度先行**：复杂业务函数先拆分职责，避免长函数、深嵌套和不可测单元，再写业务代码。
  - Go：函数尽量不超过 50 行；圈复杂度不超过 10。（go-backend-developer）
  - Python：函数行数 >80 或入参 ≥3 时，按 3-High 设计单测。（python-backend-developer）
- **API 字段类型按语义设计**：`*_id`、`*_ip`、`*_port`、`*_at` 等字段在**设计时即确定语义类型**，禁止默认 `string`（Go）/ `ContentString`（Python）。详见 `go.md` / `python.md` 中的字段类型映射表。
- **错误处理设计前置**：错误码、异常类型（Visible/Invisible）、错误上下文在写业务逻辑之前先定，禁止边写边补。
- **审计与 i18n 设计前置**：CRUD mutation API 在设计阶段就确定是否接入 audit/ulog（写明无需接入理由也可）；用户可见中文字符串从第一行就使用 i18n wrapper。

## 1. 分层与职责

出处：go-backend-developer（SKILL.md §2.2.0、§核心原则）/ python-backend-developer（SKILL.md §3.2.0）

- 复杂业务函数先拆分职责，避免不可测单元；两个 skill 均要求"参数过多时用结构体/对象封装，禁止布尔/标识参数控制分支"。
- Go 侧补充：使用接口实现多态，包之间尽量调用接口而非具体实现（go-checklist.md §5.9，见 `go.md`）。
- Python 侧补充：禁止使用全局变量，采用类加静态变量的方式实现（python-checklist，见 `python.md`）。

## 2. 命名约定（跨语言通用）

出处：go-backend-developer / python-backend-developer 共享的「通用编码checklist.md」（两份文件内容完全一致）+ 各自语言 checklist

- 禁止使用拼音、无意义字母、单个字符命名（循环变量 i/j/k 除外）【强制】。
- 标识符禁止与内置名称重名；不得出现仅靠大小写或相似字符（l/1、O/0）区分的相似标识符【强制】。
- 函数名至少 3 个字符。
- 判断类型标识符（bool 变量、bool 返回值）以 Has、Is、Can、Allow 等判断性动词开头【建议】。
- 作用域越大、影响逻辑越多的标识符取名越完整；作用域越小取名越简练【建议】。
- 在变量的作用域内，一个变量不用作多个用途【建议】。
- 各语言细化规则见 `go.md`（大写开头导出等）与 `python.md`（Py2/Py3 命名章节）。

## 3. 错误处理风格

出处：go-backend-developer（SKILL.md §2.3 + go-checklist.md §2）/ python-backend-developer（SKILL.md §3.3 + Daedalus 前置规则）

- **先日志后抛出**：抛出、包装或返回错误前必须先输出 error 日志并带关键上下文（python-backend-developer 前置规则）。
- **禁止吞错**：
  - Go：禁止忽略 error 返回值（`result, _ := riskyOperation()` 禁止）；业务逻辑禁止 `panic(err)`（go-backend-developer）。
  - Python：禁止裸 `except` / broad `except Exception`；禁止 `except` 中 `pass` / `continue`（python-backend-developer）。
- **错误必须带上下文**：错误信息作为最后一个返回值返回（Go）；错误包装保留原始错误（`fmt.Errorf("...: %w", err)`）。
- **业务错误用项目异常类型**：禁止用内置异常表达业务错误；Python 使用项目已有 `VisibleEx*` / `InvisibleEx*` / 业务错误类型并携带 errcode；Go 使用 `VisibleError`（Code + Message + Err）。
- **错误码**：定义并使用错误码（格式：`模块_资源_操作_ERROR`），不使用硬编码错误数字。
- **用户可见消息三段式**：`VisibleEx` 消息包含当前操作、失败原因、处理建议（python-backend-developer / code-compliance-check VISIBLEEX-MSG-01）。
- **panic 语义**（Go）：panic 仅用于不可恢复错误；例外是程序初始化阶段（go-checklist.md §2.2）。

## 4. 日志与 i18n

出处：go-backend-developer（SKILL.md §2.4）/ python-backend-developer（SKILL.md §3.4）

- 使用 logger（`log.Printf` / `logger.xxx`）而不是 print；后台服务禁止 print 调试信息。
- 错误日志必须包含资源标识（ID 等）。
- 日志级别纪律：开发环境 DEBUG/INFO，生产环境 WARNING/ERROR；实时日志用 Trace 且上线环境不启用。
- 所有用户可见字符串必须用 i18n 函数包裹：Go 用 `T()` / `I(...)` / `i18n.I(...)`，Python 用 `_()`；错误消息、日志消息、UI 文本都需要国际化；技术性字符串（配置键、API 路径）无需国际化。
- 不得先格式化后翻译（Python：不得 `_(u'...' % errno)`；Go：`T('未知错误！errno: %s' % errno)` 禁止）。

## 5. 安全（编码前置红线）

出处：go-backend-developer / python-backend-developer —— Daedalus 前置规则（两 skill 表述一致）

- 禁止硬编码 secret / token / password / key。
- 禁止敏感信息进入日志或返回值。
- 禁止 SQL 字符串拼接（含 `fmt.Sprintf` 拼 SQL）。
- 避免整数除法/溢出、除 0 等危险语言特性问题（通用编码checklist.md §6、§7）。

## 6. 并发与资源管理

出处：go-backend-developer（SKILL.md §2.5、§2.6 + Daedalus 前置规则）；Python 侧无对应章节

- goroutine 禁止错误捕获循环变量（循环内起 goroutine 必须传参）。
- HTTP response body 必须 close；资源使用完毕必须 `defer` 关闭，不能只依赖 GC。
- map / channel必须 `make` 初始化；channel 多生产者关闭要安全。
- 使用 context 控制 goroutine 生命周期。

## 7. 测试与覆盖率要求

出处：go-backend-developer（SKILL.md §4 + go-checklist.md §4.1）/ python-backend-developer（SKILL.md §3.2.0）

- **项目必须提供单元测试**（go-checklist.md §4.1【强制】）；核心逻辑要有单测覆盖（go-backend-developer 目标第 6 条）。

- Go 测试框架选型：GoConvey（组织用例）+ GoMonkey（打桩）+ sqlmock（DB mock）；测试文件与被测文件同包，`xxx_test.go` 命名，`TestXxx` 开头，写明每个用例的注释（详见 `go.md` 末尾的单测规范副本）。
- 注意：两个源 skill 均声明"不涉及测试编写"，测试规范以源文件为准，这里只保留编码前置阶段就要考虑的测试设计要求。

# 通用编程规范 (General Programming Standards)

## 1. 风格规范 (Style Guidelines)

### 1.1 缩进
- 使用4个空格或1个Tab缩进 【建议】
- 不允许使用8个空格缩进 【建议】

### 1.2 标识符命名
- 标识符命名要有明确含义，使用驼峰命名法 【建议】
- 函数名至少3个字符 【建议】
- 禁止使用拼音、无意义字母、单个字符（i、j、k等循环变量除外） 【强制】
- 禁止使用下划线开头，除非是常量定义 【建议】
- 不以拼音命名，不使用无意义的字母组合 【强制】
- 标识符的命名应保持一致性，不要出现仅靠大小写区分的相似的标识符，或是使用相似字符区分，比如'l'(小写字母L)与'1'(数字1)；'O'（大写o）于'0'（数字0） 【强制】
- 标识符禁止和内置名称重名 【强制】
- 函数命名可使用全小写加下划线或者大小写混杂的方式命名，不使用全大写的命名方式，不使用少于三个字符的函数名字 【建议】
- 变量可使用全大写加下划线，全小写加下划线，或大小写混杂三种方式中的任意一种；作用域越大，影响逻辑越多的标识符，其取名越完整。作用域越小、影响面越小的标识符，其取名越简练 【建议】
- 标识符为判断类型（如变量为bool类型，函数返回值为bool类型），则名称应以Has、Is、Can 或 Allow 等判断性动词开头 【建议】
- 常量名称不应该和常量值的字面意思重复，而应该解释其值所表示的内在含义 【建议】
- 变量的名字和实际用途相符，不使用和实际用途完全无关或相反的命名 【建议】
- 在变量的作用域内，一个变量不用作多个用途 【建议】
- 如果变量有多个取值范围，且各取值范围代表不同意思，须保证各个取值范围之间不得有重叠 【建议】

### 1.3 注释规范
- 所有导出的函数、类型、常量必须有英文注释 【建议】
- 文件头包含作者和修改者信息 【建议】
- 整个项目均使用英文注释 【建议】
- 注释应该解释"为什么"而不是"是什么" 【建议】
- 注释应与其描述的代码相邻，放在代码上方或右方 【建议】
- 注释内容要准确、简洁、清楚 【建议】
- 对重要的算法、复杂的业务逻辑、临时的解决方案必须有注释 【建议】

### 1.4 代码格式
- 行长度不超过80列 【建议】
- 使用UTF-8编码和Unix换行符 【建议】
- 代码重复率不超过10%，不允许连续15行以上重复代码 【建议】
- 空行应该用来分隔逻辑相关的代码块 【建议】
- 在函数、类、结构体定义之间应该有空行 【建议】
- 在相关的代码组之间应该有空行 【建议】
- 在函数内部，逻辑相关的代码块之间应该有空行 【建议】

### 1.5 冗余代码
- 删除无用的代码、注释、变量 【建议】
- 删除无用的import/include语句 【建议】
- 删除调试用的代码 【建议】
- 删除注释掉的代码 【建议】

### 1.6 重复代码
- 必须检查复制粘贴的重复代码，防止出现修改不全的问题 【建议】
- 超过5行的重复代码应提炼成函数 【建议】
- 重复代码指出现次数超过2次且只有变量名字或常量内容不同的代码块 【建议】

### 1.7 圈复杂度
- 函数的圈复杂度不应超过10 【建议】
- 如果函数的圈复杂度超过10，建议拆分成多个函数 【建议】

### 1.8 TODO注释
- TODO注释应该包含具体要做的内容和负责人 【建议】
- TODO注释应该有时间限制 【建议】
- TODO注释应该在完成后及时删除 【建议】

## 2. 错误处理 (Error Handling)

### 2.1 参数验证
- 对接口函数的参数进行验证 【强制】
- 验证外部输入数据有效性 【强制】
- 所有从模块外部读取的数据必须先检查有效性 【强制】

### 2.2 返回值检查
- 函数返回后，必须先检查函数运行的正确性 【强制】
- 执行合适的错误处理 【强制】
- 例外：1）函数运行不会失败；2）函数运行失败对后续逻辑正确性没有任何影响 【建议】

### 2.3 数据有效性检查
- 检查从文件、数据库、标准输入、命令行参数、管道、socket等获取的数据 【强制】
- 避免不合法数据进入后续流程 【强制】
- 不使用断言等仅在调试版本生效的措施 【建议】

### 2.4 错误处理原则
- 错误处理分几个环节：错误检测、错误传播、错误阻断、错误纠正、错误消除或终止 【建议】
- 错误检测：检查发现数据不在预期有效范围 【建议】
- 错误传播：将错误传递到适合处理的位置 【建议】
- 错误阻断：中断正常业务逻辑执行 【建议】
- 错误纠正：清理异常数据，回到合法状态 【建议】

### 2.5 日志
- 实时日志使用Trace级别，应用上线环境不能启用Trace级别 【建议】
- 开发环境使用DEBUG或INFO级别，生产环境使用WARNING或ERROR级别 【建议】
- 错误日志需包括资源标识信息 【建议】
- 后台服务不允许使用print打印调试信息 【建议】

## 3. 函数 (Functions)

### 3.1 重复代码提炼
- 超过5行的重复代码应提炼成函数 【建议】
- 如有效率要求，可将函数内联 【建议】
- 重复代码指出现次数超过2次且只有变量名字或常量内容不同的代码块 【建议】

### 3.2 函数实现
- 不允许在函数参数中使用布尔类型 【强制】
- 避免使用标识参数控制函数执行逻辑 【强制】
- 函数递归调用必须考虑收敛条件 【强制】
- 设计高扇入，合理扇出（小于7）的函数 【建议】
- 函数本地变量数量不应超过10个 【建议】
- 函数参数个数不超过5个 【建议】

## 4. 语句 (Statements)

### 4.1 代码复制粘贴
- 必须检查复制粘贴的重复代码，防止修改不全 【建议】

### 4.2 循环性能优化
- 可以在循环体外进行的耗时计算不放入循环体中 【强制】
- 如果循环体内存在逻辑判断且不会改变，应将逻辑判断移到循环体外 【建议】

### 4.3 控制结构嵌套
- 循环嵌套不超过3层，总共不超过5层 【建议】
- 建议使用短路返回方法减少嵌套层数 【建议】

### 4.4 表达式
- 不可将浮点变量用"=="或"!="与任何数字比较 【强制】
- bool变量直接进行真假判断，无需与true/false比较 【建议】
- 不可同时在循环语句和循环体里修改循环变量 【建议】

### 4.5 复杂表达式
- 不使用过于复杂的表达式 【强制】
- 三目运算符不允许嵌套使用 【强制】
- 鼓励把复杂表达式分拆成多句书写 【建议】

### 4.6 if语句
- 将执行概率较大的分支放在前面处理 【建议】
- if子句和else子句行数相差超过3行时，else子句应比if子句长 【建议】
- 两个值判断时，变量在左，常量在右 【建议】
- 减少不必要的else 【建议】
- 用switch替换多个相似的if语句 【建议】

### 4.7 复杂else if语句
- 不允许写过于复杂的else if语句 【建议】
- 如果子句会中断执行，采用短路返回 【建议】
- 尽量减少if...else的嵌套 【建议】

### 4.8 类型转换
- 禁止有符号类型和无符号类型相互转换 【强制】
- 禁止将较大整型转换为较小整型 【强制】
- 若需转换，必须显示转换并注释说明 【强制】

## 5. 网络 (Network)

### 5.1 避免大小端错误
- 涉及大小端数据处理时，需要进行大小端判断 【强制】
- 保存大小端数据的变量命名，建议增加n/h前后缀 【建议】

## 6. 内存 (Memory)

### 6.1 栈溢出
- 使用栈上内存需要考虑是否存在栈溢出问题 【强制】
- 注意递归调用过深和大量局部变量 【建议】

### 6.2 整数溢出
- 避免整数溢出 【建议】
- 如果使用整数反转特性，必须添加注释说明 【建议】

## 7. 危险的语言特性 (Dangerous Language Features)

### 7.1 时间间隔
- 计算时间间隔禁止使用系统日历时间函数 【强制】
- 应使用系统开机时间的函数 【强制】
- Windows平台必须使用GetTickCount64 【强制】

### 7.2 除0错误预防
- 用作除数的变量需保证不为0 【强制】
- 求余运算符的右操作数也需保证不为0 【强制】
- 来自不可信输入的变量必须先判断是否为0 【强制】

### 7.3 移位运算
- 移位运算的右操作数必须大于等于0并小于左操作数的位数 【强制】

### 7.4 文件锁
- 对于通过文件句柄持有的文件锁，不能使用截断模式打开文件 【强制】
