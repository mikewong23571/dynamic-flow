# 工作项分治方案 v2：围绕问题开始，按需要拆分

日期：2026-10-23。状态：修订设计，未实施。依据上一版独立审查重写；不代表用户已确认所有交互或现有应用具备这些能力。

前版问题见[独立审查](evidence/design-v1-review.md)。本文为产品设计基线；源码调研后的具体承载与取舍以[实施设计](implementation.md)为准，验收见[页面故事](acceptance.md)。

## 1. 用户需要理解的事情

用户只需要围绕五件事工作：要解决什么、哪些部分需要分别处理、已有材料、得到的结论、是否完成。

创建时不要求区分聚合工作项和执行工作项。一个问题可以直接处理，也可以在开始或处理中拆成子问题。建立子项不更换原问题身份，也不抹去原来的处理记录。

工作项是一个可以独立推进和确认完成的问题。父子关系表达问题分解；流水线表达一次处理的方法。这两个关系不合并。

页面以实际内容组织：没有子项时突出当前问题和处理入口；有子项时突出子项进展和待办，同时保留本项材料、成果及处理入口。用户不必切换类型才能获得对应操作。

## 2. 连续用户故事

### 2.1 拿到报告，先把工作放下来

小林拿到产品 A 的季度扫描报告。他新建“产品 A 本季度漏洞核查”，写下要查清的范围，上传报告并保存。

页面显示目标和报告，并提供“开始处理”“拆分工作”。他无需先准备流水线，也无需判断这是聚合还是执行工作。没有现成方法时，沿用应用已有的选择或生成方法入口。

这次报告里有上千条线索，他选择拆分工作。选定整理方法后，刚上传的报告已带入；他可以展开检查或换材料，确认本次处理范围后开始。

验收：仅填写目标和已有材料就能保存；选择拆分时无需重新上传或重新找到同一份报告。

### 2.2 看清拆出来的是什么，再一起建立

处理完成后，小林看到一张问题清单。每行显示准备跟踪的问题、范围、已有材料，以及是否已有关联工作项。

清单按“可建立”“已关联”“需补充”区分。小林可以就地改目标、取消不需要跟踪的记录、查看材料，也可以直接批量建立选中的有效记录。必填目标或范围缺失的条目明确列在需补充区，不阻止其余条目建立。

建立之后，原行变成对应工作项的入口，再次打开清单仍然如此。普通成果列表不会凭出现一个数组就自动创建事项。

以后再追加扫描报告，相同跟踪标识的记录显示已关联工作项，不自动再建一份，也不覆盖已有结论。新增材料可以明确补到已有项；已结项的记录若需要继续，补充操作同时提供重开。不能确定对应关系的记录允许关联当前父项下的已有项或新建，不以模糊相似度静默合并。首版不支持把另一父项的工作项直接改成多归属；可以引用其成果作为材料，但不改变责任关系。

验收：批量建立无需逐条打开表单；同一清单重复点击不重复创建；追加扫描已有项可见且可进入；不把新增证据悄悄当成结论。

### 2.3 批量开始处理，缺什么就处理什么

小林选中准备核查的一批问题，点击开始处理并选择核查方法。应用按照拆分时保存的材料及方法声明准备各项输入。

开始前，页面显示选中数量、准备就绪数量和缺少输入的项。准备好的项可以一起启动；小林不需要对每一项重新做一遍材料选择。需要时可以展开任一项查看实际输入并修改。系统不猜测含义不明的输入绑定，有歧义的项留在需补充区。

启动后，各项拥有自己的运行和处理状态。某项失败只影响该项，不把整批显示为失败，也不要求成功项重跑。批量操作返回逐项结果，失败项留在当前列表可继续处理。

验收：分别准备、冻结每项的实际输入；批量操作不把所有材料混给每个工作项；一项缺材料或启动失败不吞掉其他项结果。

### 2.4 处理中才发现两个仓库

其中一个问题是“核查 CVE-X 对 target A 的影响”。调查之后才知道 target A 包含仓库 A 和仓库 B，需要分别核查 develop 分支。

流水线在结果中给出两个子问题：各自目标、仓库和分支、已经取得的漏洞材料、还需要完成的核查。小林在这里直接建立两项。原问题不需要改类型，原调查记录仍在；页面出现两个子项。

如果此次调查已经得到仓库 A 的可靠核查结果，清单同时显示它的已有结果。小林可以在建立时一并确认其完成依据；没有检查依据时，它保持未完成，但再次打开就能读取已有结果，不必重跑。仓库 B 信息不足，带着已有材料继续。

如果两个仓库只是同一个判断中的两份证据，不能独立处理或验收，小林可以不建立子项，继续在当前问题中处理。这是业务判断，系统不凭结果数量自动决定。

验收：创建时不知道会拆分的工作项也能拆分；已有结果可接续；建立待办和确认已有结果的含义不同，默认不自动结项。

### 2.5 第二天，从整体入口找到真正需要自己的地方

小林回到季度工作项。默认显示本范围内的待处理事项：需要补材料、运行失败、待检查结果，以及子项已完成而需要整体确认的问题。列表保留所属问题，重复的纯汇总行不与实际待办混为同一计数。

他筛选需要补材料，直接找到“target A / 仓库 B”，不需要先打开所有 target。进入详情后，页面显示缺少的版本材料、已知仓库和原方法。若缺少的是目标输入里的分支字段，他就在该条输入上填入develop，保存修订后点击继续；若新增的是一份独立证据，则追加材料。准备页沿用原方法和其余已确定输入，显示本次替换或新增的内容，不把“补字段”当成再塞一段说明。

如果缺口仅来自 Agent 的自由文字，页面提供该提示和普通补材料入口；只有方法已声明的字段才形成可填写字段，不把任意文字自动转换成表单。

完成处理后返回，季度列表保持原筛选和位置。他仍可以切换查看直属子项，以了解整个问题如何组织。

验收：季度→target→仓库三层情况下，一次筛选可以定位仓库待办；补材料后明确进入下一次处理，不需要重新配置所有已知信息。

### 2.6 确认具体结果，再回到整体

仓库 B 得到结果后，小林检查成果和完成条件，点击确认完成。系统将这次确认的依据和成果来源保存在完成记录中；不要求再写一份重复的结论，也不另设独立审批步骤。

回到 target A，两个仓库结论直接列在一起。若已经能回答原问题，小林检查整体条件后直接确认完成；若确实需要分析和撰写综合报告，再选择汇总成果。汇总默认带入两个子项已经确认的完成依据，显示来源和未覆盖范围；小林只在需要换用其他结果时修改。

汇总固定本次选中的完成记录及成果版本，不自动把最近一次模型输出当成结论。允许在部分子项未完成时生成阶段报告，但未完成部分仍保留，生成报告不使工作项结项。

季度工作项以同样方式收拢各项结果。整体待办列表显示需要确认的父项，避免要求用户记住逐层回去收尾。可以批量确认具备完整依据、没有额外判断的项；未满足条件的项留在列表说明原因。

验收：不要求每层都运行汇总方法；确认过的结论可以默认作为汇总输入；运行成功、报告产生、用户确认完成仍然不同。

### 2.7 正常调整范围，不制造假完成

小林发现一个仓库实际不在本季度范围，选择移出本次范围并填写原因。工作项和此前证据保留，季度项仍能查看这条排除记录，但它不再阻止季度工作完成，也不会显示为已经核查完成。

如果新证据要求重开一个已完成子项，或者在已完成父项下新增未完成子项，当前操作会明确显示哪些已完成的上级问题也需要重开；确认一次后一起处理，不要求小林逐层寻找。已明确配置自动建立子项的方法也遵循同一规则，运行准备时展示会重新打开相关工作范围，不能静默保留父项已完成状态。此前报告和完成记录保留，当前状态重新反映存在未完成部分。

验收：范围排除不等于结项或删除；重开不改写旧结论，也不自动重跑或重写汇总报告。

## 3. 页面所承担的工作

### 创建

只收集目标、已有材料和可选范围/完成要求。不出现必选聚合／执行类型。

### 工作项详情

- 无子项：当前目标、已有成果、需补充事项和开始/继续处理入口。
- 有子项：本范围待办优先，可切换直属子项及全部事项；保留本项材料、成果和处理入口。
- 上级问题作为可返回的位置入口；列表返回保留筛选和位置。不建立常驻巨大树。
- 身份、执行状态与完成情况分别表达，避免用“推进”掩盖启动、补充、重试、检查和结项等不同动作。

### 拆分清单

列：问题、范围、已有材料/结果、建立状态、必要操作。先显示需要用户判断的内容；来源、方法、运行等按需查看。支持批量建立、关联已有项和取消选择。

### 批量处理准备

显示方法、选中范围、可启动项和需补充项。系统准备逐项输入，用户可以展开检查和修改。不是要求用户处理一千张独立配置表。

### 完成与汇总

直接使用已有完成条件和依据确认能力。完成时固定被认可的依据；有子项时默认展示它们的已确认结论。额外分析才运行汇总方法。

## 4. 内部领域模型

### 4.1 一个业务实体：WorkItem

复用现有 WorkItem，不新增并列的事项实体，不新增聚合／执行的业务类型。

保留目标、data、材料、条件、业务状态、历史、运行关联。最小增量：

- parentId：可选，记录所属问题。父项不内嵌全部子项内容。
- parentScope：该父子关系是否计入父项范围；移出时记录原因和时间。它不是子项的完成状态。
- origin：可选，记录候选来自哪个固定成果输出，或自动建项节点保存的哪份输入，以及candidateId；供清单反馈和重试关联，不从粗粒度来源猜输出位置。
- trackingKey：可选，在同一父项下识别同一个跟踪问题，由明确的拆分方法提供。它不等于标题，不由应用猜测 CVE 或仓库字段。

没有 parentId 的现有工作项保持独立根项，原有数据不需要为了此功能先分类。已移出范围的子项保留原parentId及历史，父项默认进行中统计排除它；仍可通过移出范围筛选查看。

父子关系表达持续责任，不是流水线依赖边。一项可有多个子项和多次运行；一轮运行仍归属一个工作项。一个子项只有一个父项，首版关联已有项仅在当前父项内选择。范围统计、完成阻塞和重开传播只沿仍计入范围的父子关系计算；移出范围的子项继续处理不影响已排除它的整体工作。若重新纳入未完成子项，明确恢复范围并按同一规则重开相关已完成父项。

### 4.2 拆分候选是运行输出，不是新工作项

候选的最小内容：

    标识（可选 trackingKey）
    标题与目标
    范围数据
    初始材料/已有成果及来源
    完成要求

候选由 Agent 或用户组织。手工从成果建立读取固定输出；自动建立读取该节点首次保存的固定输入，并在回执中保留引用，恢复和补建沿用同一来源。允许用户编辑确认后保存子项。编辑后的实际目标与输入存入子项，来源仍保留。

建立结果关联候选和实际工作项。人工确认和流水线配置的自动建立使用同一个业务动作，结果都显示已建立或已关联，不出现“实际上已自动建项，页面还提示新建”的两条路径。

同一次候选建立重试按来源复用既有子项。后续扫描的trackingKey在同一父项内匹配已有问题；有冲突时显示并要求处理，不静默覆盖目标或完成状态。没有稳定key的候选只保证同一来源不重复，跨运行可手工关联，不宣称能自动理解任意业务重复。

这是一项明确业务动作，不需要新增通用工作流编排平台。流水线未配置该动作时，普通输出只能形成候选，不产生工作项。

### 4.3 材料交接与本次输入

子项建立时保存其明确的初始数据和材料，结构化值保持结构化，并保留来源引用。不会继承整个父项历史，也不会复制上千项无关资料。

复用已有材料/成果选择机制，增加“已交接输入”的可选来源：值和来源保存在子项中或通过不可变成果引用解析。准备运行时按方法声明匹配已准备输入，用户看到的是业务材料；无法确定的入口需要选择，不进行隐式语义猜测。

结构化输入需要补齐或修正时，保存新输入ID并关联旧值，准备页只替换对应选择；追加独立证据是另一种操作。原成果与旧Run保持不变。

本次运行仍冻结实际值、来源和方法版本。默认带入只是减少重复操作，不降低输入可见性和可追溯性。

当前代码 resolveItemInputs 限定来源 Run.workItem.id == 当前项，需要扩展为允许本项已经明确交接的来源。不能仅删除条件并认为跨项交接已经完成。

### 4.4 被确认的结论使用完成记录承载

复用已有完成条件、依据与完成历史，扩充精确成果来源字段，完成时保存该次条件/证据及必要的所选子项完成记录快照。

不新增一套独立的“发布结论”流程。用户确认完成即确认本次依据；人工完成没有成果文件时，已有文字依据也可表达结论。

父项汇总引用子项完成记录（itemId + completionHistoryId）及其成果来源，而非读取子项当前可变summary或最新Run输出。重开之后旧完成记录仍可追溯，但当前项未完成，默认汇总将其列为未完成范围；用户明确选择历史结果时标为历史依据。

子项全部完成不自动结项父项。没有额外汇总任务的父项可直接检查既有依据后确认；有独立判断要求时仍需完成这些要求。

### 4.5 父项视图与规模

直属子项列表回答“问题如何组织”；范围内待办回答“现在需要处理什么”。两者由简单父子关系计算，不新增项目实体或任意依赖图。

默认分页加载所需摘要，不读取每个后代完整运行。待办集合包含有实际动作的后代，以及需要独立检查/整体确认的父项；展示所属问题。不用递归嵌套UI来承载上千项。

1000项的列表/查询成本需要实际验证。若现有单文件存储的查询不满足，再为摘要查询增加最小索引或缓存；不在设计阶段假设必须更换数据库。

## 5. 自动化边界

- Agent 负责发现子问题、整理初始材料、提出完成要求；应用负责工作项身份、关系、来源和保存结果。
- 建立子项默认可以在清单上批量确认。某方法明确配置自动建立时，正式运行可直接建立；用户运行前能看到该方法包含此动作。试运行只产生候选。
- 建立子项不会自动递归启动所有子项。父项这一轮处理可结束，子项后续通过单项或批量动作启动。
- 批量启动是多个普通工作项启动动作的组合，逐项返回结果；等待和中断留在待办，不占用后续新启动名额。已有Run按现有信号、到期或显式恢复继续，恢复后重新计数，达到启动阈值就暂缓新增，不取消恢复中的Run。该阈值不承诺全局硬并发，首版不建设父子运行调度器。
- 重开不自动生成新结论或重跑；范围移出不删除原历史。

## 6. 分步交付与真实验收

### 第一步：问题可拆开，各自继续

用户创建时没有类型选择；可以手工建立子项；当前项有材料即可处理。子项带入所选材料，进入/返回保持位置，能独立继续。以“起初不知道两个仓库，后来拆开”为主验收。

完成检查沿用已有能力，补齐父项范围内未完成子项的约束、必要的重开和移出范围操作。不能只增加parentId就标为用户故事完成。

### 第二步：从实际处理结果建立子项

接入拆分清单、来源关联、已建立反馈及结构化材料交接。用10条候选验证批量建立、重复进入、普通重跑关联、已有成果带入以及无需重跑的完成确认。再接方法中明确配置的自动建立，复用同一业务动作。

### 第三步：在整体范围内批量推进与收尾

提供跨层待办、批量输入准备与逐项启动结果；汇总默认引用完成依据，没有额外分析时直接整体确认。

至少使用1000项和季度→target→仓库的多层数据验证：从根定位具体缺口、只处理未准备项、列表分页、部分启动失败、已确认成果汇总、返回保留。报告用户实际需要逐条操作的场景及数量，不能只报告渲染用时。

第二步结束可以称为小规模分治闭环，不能宣称已经解决上千漏洞跟踪。

## 7. 与原稿的主要不同

1. 去掉没有独立业务规则支撑的聚合／执行类型。
2. 明确输入是系统保存义务，已知材料默认接续；用户只处理范围、缺项和歧义。
3. 整体入口可跨层定位待办，而非依赖逐层展开。
4. 拆分建立的是问题；已有成果表达已做工作，不能直接用成果标题代替目标。
5. 清单记录已关联状态，并处理正常追加扫描的已有问题关联。
6. 不要求每个父项再跑汇总；采用已有完成记录承载认可结论，不新增发布流程。
7. 把补充并继续、范围移出、整体确认写成可操作的故事，不以状态字段代替用户路径。
