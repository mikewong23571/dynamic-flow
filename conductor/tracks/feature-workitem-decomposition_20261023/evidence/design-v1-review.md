# 工作项分治方案：独立审查

日期：2026-10-23。审查对象：`/tmp/flowcraft-workitem-decomposition-review.md` 第 1–6 节原始草案。

范围：只审查产品故事、认知负担和最小领域边界；未改代码，未验证实现。本报告独立于方案作者的既有判断。

## 结论

方向合理，但原稿不宜直接进入实施。最大风险不是模型承载不了，而是要求用户先学会如何组织模型，再完成自己的业务。

原稿让用户在创建时判断聚合/执行，在发现结果时判断是否值得成为子项，在建立时选择材料，在启动时再次选择输入，在汇总时逐份选择成果版本，再逐层确认结项。每个步骤单独看来都“明确”，组合起来却形成一条需要专门培训的操作路线。

建议保留“工作项可以拆出独立子项、运行固定输入、来源可追溯、结果不等于完成”四条基本边界；去掉强制类型选择，让材料自动接续、用户只处理缺项和需要判断的地方；补齐跨层待办和拆分清单的建立反馈。当前不需要增加调度平台或新事项实体。

## 用户到底需要提前知道什么

| 用户现在必须知道的事 | 是否属于业务必需 | 应如何承担 |
| --- | --- | --- |
| 我想解决什么、范围是什么 | 是 | 创建时填写目标和范围 |
| 哪些问题值得独立跟踪 | 是，但不一定创建时知道 | 看到具体问题清单后再判断，允许执行中拆分 |
| 聚合和执行有何区别，选错会怎样 | 否；两者能力相同 | 不作为必填领域类型，页面随内容组织 |
| 工作项、运行、节点实例、成果之间的区别 | 部分是内部概念 | 日常操作显示具体问题、材料和结果；需要追溯时才展开来源 |
| 哪些证据对应哪个子问题 | 业务需要，但已有上下文可以携带 | 拆分时自动带入对应材料，界面允许修正 |
| 每项运行要绑定哪个成果端口和版本 | 通常不是 | 方法带有明确输入，应用准备并固定版本；用户检查业务材料 |
| 何时足以确认完成 | 是 | 完成条件就地展示，合理默认和批量处理减少重复动作 |
| 如何逐层关闭、重新打开父项 | 否 | 页面展示影响并提供一次明确动作，不要求人工遍历树 |

原则：“输入明确”应主要是系统记录的属性，而不是要求用户反复做选择。用户应知道这次处理什么，但不必负责每条底层引用的接线。

## 主要问题与最小修正

### P1 — 创建时强制选择类型，没有稳定的业务差异

**反例：** 用户创建“核查 target A”，不知道包含两个仓库，选择执行；后来另一个用户创建同样目标，因为已经知道两个仓库而选择聚合。两项可以运行相同方法、拥有相同子项、使用相同完成规则，但页面可能不同。

**失效假设：** 初始认知可以可靠决定持久类型。原稿同时允许两类做所有动作，使 `role` 只剩页面偏好，却被包装成领域事实。

**影响：** 故事一、二和实施第一步。用户会担心选错类型，维护者需要解释为什么相同内容呈现不同页面。

**最小修正：** 创建只要求目标和材料。创建后可“直接处理”或“拆成子项”；有子项时显示子项列表，没有子项时突出当前问题与处理入口。这两种开始方式可以作为快捷操作，而非永久分类。若确有必须长期区分两类的业务规则，再加类型；当前稿没有证明这种需要。

`parentId` 表达真实关系，`role` 不应重复表达“是否管理子项”。父项可以有自己的运行和成果，无需转换身份。

### P1 — 材料交接被设计成三次人工接线，无法扩展到上千项

**反例：** 拆分 1,000 个漏洞时用户检查并带入材料；批量启动又要求检查各项输入；汇总再选择每项具体结论与版本。如果每项只花 10 秒，一轮确认也需要近 3 小时，且用户可能选错端口或旧结论。

**失效假设：** “显式交接”必须意味着每次手工选择。固定输入是系统义务，不是额外业务劳动。

**影响：** 故事一、三、四、五；“无需复制 JSON”还不足以证明可用。

**最小修正：** 拆分动作自动携带其确定的目标与对应材料；选定方法后系统预填本次输入，仅突出缺失或有歧义的项。批量启动显示范围、准备就绪数量、需补充数量，并允许检查样例与例外，不逐项强制确认。

汇总默认使用范围内各项已经确认采用的结论；页面展示纳入数量和未完成范围。若某项尚未选定结论，才要求处理该项。开始运行时固定实际引用，后续数据变化不改写本次输入。不能简单默认“最新一份模型输出就是结论”。结项动作可以顺带确认本次采用的成果，不需要再给用户增加一个独立接线步骤。

### P1 — 两层故事与“只查直接子项”的列表模型不匹配

**反例：** 季度项下面有 300 个 target，每个 target 又有仓库子项。用户回到季度项筛选“需要补材料”，仓库 B 的缺口在孙项；直接子项 target 可能只显示未完成。用户要打开几百个 target 才能找到需要自己处理的仓库。

**失效假设：** 有父子列表就能在整体范围定位待办。当前故事事实上已经产生至少三层，不是一个只有直接子项的平面列表。

**影响：** 故事二、五；这是故事本身立即产生的问题，不是未来的罕见树结构边界。

**最小修正：** 父项的工作列表提供“直属子项”和“全部待办”视角。后者按父项范围列出需要推进的后代，保留一列所属问题，点击进入具体项并可返回原筛选。领域仍是简单 `parentId`，不需要新增项目/集合实体，也不必做巨大可展开树。

验收必须包含“从季度项一次筛选定位仓库 B 的补材料任务”，而非只验证进入一个直接子项。

### P1 — 从成果建立子项，尚未定义用户到底在建立什么问题

**反例：** 成果 A 是“仓库 A 不受影响”，成果 B 是“仓库 B 信息不足”。用户选择二者“建立子项”，系统究竟建立“继续核查仓库 A”，还是建立“已核查仓库 A 的记录”？如果直接把成果标题当待办，用户得到两个看起来都待处理的事项，只能重新解释已经完成的工作。

**失效假设：** 任意成果都天然包含可独立验收的问题定义。数据记录、证据和待办目标不是同一件事。

**影响：** 故事三，以及普通成果到业务身份的转换。

**最小修正：** 建立前显示的是“需要跟踪的问题”清单，包括目标、范围、已有结果、还需做什么。已有结果只自动作为材料，不凭文字自动判定结项。对已经充分完成的记录，用户可以在同一批量确认中确认其完成并采用成果；对仍缺材料的记录保持待办。允许只建立确实需要后续跟踪的项，不为了凑齐树结构把每份证据都变成任务。

拆分和整理成果可以借助 Agent，但需要使用同一份明确的候选工作项形状，不能让用户理解端口/schema 后才能完成转换。

### P1 — 手工与自动建立是两条不完整的路径，容易在日常重跑时重复生成任务

**反例：** 首次扫描处理后已经建立 500 项。用户补充文件后重新运行，页面又展示一份近似清单；当前稿只保证“同一次建立动作”重试不重复，用户不知道哪些已建立。或流水线执行时已自动建立，成果页仍提供同样的建立按钮。

**失效假设：** 成功建立是一个瞬间动作，不需要在原清单里持久可见；跨运行重复扫描是罕见异常。对漏洞跟踪，这属于正常工作。

**影响：** 故事一、二、五和自动拆分设计。

**最小修正：** 所有路径使用同一个建立动作和同一种结果：候选条目显示“未建立/已关联工作项”，建立后入口变成打开工作项。手工确认是首版默认；自动执行是方法的明确配置，不能由模型临时决定。对于追加/重跑，至少允许候选“使用已有子项”或“新建”，已有来源明确相同时自动关联。

不要求做跨全部业务的智能去重系统。第一版只需保证同一来源条目不会反复建立，并在同一父项下让用户看见/选择已有项；无法判断相同的问题不要静默合并。文档需诚实说明首版未自动识别任意改写后的同一业务问题。

### P2 — 多层结项容易形成纯粹的行政操作，且正常的范围调整没有出口

**反例一：** 1,000 个仓库项已核查，每个 target 还需要选择成果、运行汇总、确认自身条件，季度层再做一次。若 target 没有额外业务判断，这些操作只是在把状态一路搬上去。

**反例二：** 核查后发现某仓库并不属于本次范围。原稿“任何未完成子项阻止结项”迫使用户伪造已完成，或删除记录。

**失效假设：** 每个父项总有独立的汇总任务；所有建立过的子项永远都是完成前提。

**影响：** 故事四、规则五、完成/重开路径。

**最小修正：** 不强制每个父项都跑汇总方法。有额外总体判断时才需要汇总；没有时展示子项结论并直接确认整体完成。范围调整应允许明确移出本次范围并保留原因，移出项不计入完成阻塞。使用已有可用状态/关系动作，首版不需要依赖图和复杂状态机。

子项重开时，同一个动作展示并处理受影响的已结项父项，不让用户逐层寻找；保留旧报告历史，明确当前工作又有未完成部分。不要自动生成新的报告，也不要凭重开就宣布所有旧结论错误。

### P2 — “需要补材料”尚未连接到具体用户操作

**反例：** 仓库 B 待定。用户在季度列表筛选后进入，看到历史报告说“缺少版本信息”，仍不知道把分支填在哪里、补完后重跑哪个方法、已提供材料是否会被使用。

**失效假设：** 状态、结果和运行按钮同时存在，就形成下一步。原稿故事在“补材料后重跑 B”这里跳过了实际操作。

**影响：** 故事三、五，是认知负担最容易暴露的地方。

**最小修正：** 子项详情直接展示待补字段/材料及已有值，提供“补充并继续”操作，沿用上一方法和已确定输入；用户可调整，但无需从空白配置开始。完成后回到原待办筛选。首版只支持方法已声明的输入和用户上传材料，不需要一个通用自动规划系统。

## 当前仍然合理、应保留的边界

- 工作项是持续问题身份，运行是一次固定输入处理；来源和历史不能为了拆分被改写。
- 子项与节点没有一一对应关系，普通集合输出不自动建立业务身份。
- 子项仍复用 WorkItem，不新增平行“事项”实体。
- 父项可以运行材料整理和汇总，不能仅因它有子项就禁止运行。
- 父项运行在完成建立动作后结束，不维持一个长时间等待全部子项的 Run。
- 结果待定、运行成功和业务完成分别表达；不能用自动完成掩盖缺口。
- 页面按列表筛选和定位，详情才加载完整过程；这是合理的规模路径。

## 建议替换成的最短故事

1. 小林创建“本季度漏洞核查”，上传报告。系统不要求他判断工作类型。
2. 他点击“拆分工作”，选择整理方法；系统根据报告生成问题清单。他确认范围后批量建立，已建立项可直接进入。
3. 他批量处理准备就绪的项；系统带入拆分时已有材料，单独列出缺少输入的项。
4. 某项处理发现两个仓库，呈现两个可独立推进的问题；小林建立子项，已有调查成果自动带入。
5. 第二天他从季度项筛选全部待办，直接找到仓库 B，补上缺少的版本信息，继续处理；不用重新配置仓库 A。
6. 他回到 target，看到已确认的仓库结论。有必要时运行汇总，否则直接检查并确认整体完成；季度项仍能看到剩余待办。

这条故事要求用户理解“目标、子问题、材料、结论、完成”即可。类型、成果引用版本、运行归属、节点端口由系统承载，必要时可追溯，而不成为开始工作的先修知识。

## 建议推进顺序与验收

第一步：创建目标、手工建立子项、返回、分别处理。不要先做没有区别的类型枚举。验收应包含“创建时不知道会拆分，之后仍能拆出两个仓库”。

第二步：拆分清单、自动携带材料、建立状态反馈。验收包含 10 条记录批量建立、再次进入不重复建立、已有结果接入子项后不重跑也能阅读和确认。

第三步：批量准备/执行、跨层待办、按确认结论汇总。必须以 1,000 条候选和至少两层子项验证列表与批量操作；并检查用户需要逐条处理的是否仅限真实例外。不能用 2 个仓库的成功操作证明千条工作已经可用。

以上为设计审查建议，不代表功能已实现。原型可先交付小规模完整路径，但应明确规模边界，不宣称第一步已解决上千漏洞跟踪。
