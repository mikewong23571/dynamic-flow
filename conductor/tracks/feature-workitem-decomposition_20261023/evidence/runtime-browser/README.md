# 独立浏览器验收：生命周期、批量推进与千项规模

实现与测试职责分离：runtime子代理仅新增 `tests/browser/workitem-decomposition-lifecycle.spec.ts` 和此证据；产品修复由 frontend/backend 代理完成。所有操作在临时 dataRoot + 私有 Hono HTTP 服务，模型为受控 fixture，没有写真实业务数据或调用千次真实模型。真实 Pi high 小样另见 `../runtime/README.md`。

## 页面故事

- 两尺寸（1440×900、1024×768）检查已确认子项结论，选择完成记录汇总，确认无独立文字条件的父项与祖先；重开B明确影响祖先，排除/恢复范围；旧父完成事件仍指向B首次完成，旧汇总Run输入不改。
- 两尺寸：12项中10项输入完整，2项缺ref。页面准备显示10可启动/2需补充，只对2项做字段修订；返回批次保留状态，12项各启动一次，未要求逐项端口映射。
- 窗口：A/B使用明确等待方法，C–H使用直接核查方法；每节点each/concurrency=2，每项2个输入。等待释放启动名额，应用重建后中断也释放；页面resume C与signal A保持原Run ID，活动恢复到4时不新增G/H。暂停后两个未提交项保持0Run，已启动项完成后页面更新真实状态。
- 规模：100 target + 1000叶子，每叶20段业务历史、4轮实际长度结果，共享方法约62MB。完整标题搜索父项可在第一页进入；范围内待办筛选直接找到仓库777及所属目标77；进入详情、填写草稿、返回保留筛选。列表只返回摘要、每页25行，详情方法请求只取选中项4个Run。

## 容量、时间与边界

`baseline-scale-*.json` 保留修复前数据：筛选约4秒、返回约3.5秒；后端增加按文件版本的解析缓存及同版读取合并，摘要复用，同时保留调用方独立副本及写入失效。

`scale-{1440,1024}.json` 记录各尺寸三轮实际请求、响应字节和页面可操作时间：

- `firstListMs`：点击“工作项”到第一条业务行按钮可见；不只测HTTP。
- `listMs`：完整进入链路（goto→工作项→标题搜索→打开父项→直属列表可见），不能与一次首屏混为一谈。
- `filterMs/openMs/backMs`：实际筛选到匹配行、打开单项、返回保留列表状态。
- 首次服务端缓存未命中，后两次浏览器重新载入但服务端缓存已暖；每轮返回是当前页面热返回。

当前最新实测：冷UI首屏2.52–2.66秒，热首屏0.38–0.43秒；筛选0.11–0.15秒，打开单项0.73–0.86秒，热返回0.10–0.15秒。冷完整多操作链路约3.4秒。**冷UI首屏未达到最初建议2秒预算。** 按 track 允许“定位并修正或明确调整预算理由”的约定，编排者明确将本62MB历史fixture的冷首次UI列表预算调整为3秒，实际2.52–2.66秒在该边界内；热首屏/筛选仍保持2秒、热返回仍1秒。原因是保留原型JSON文件存储的一次解析成本，不再将开销转嫁到每次运行保存/预热，也不为约0.6秒引入存储平台。原始2秒建议、未达值和3秒取舍均保留；不能表述为“全部首屏2秒内”。

`batch-window.json`：新启动阈值2，实测Run峰值4、Agent峰值8；恢复允许临时超阈值，未宣称全应用硬并发上限。此处是应用close/recreate恢复，非OS子进程重启；已有子进程恢复测试属于相邻模块证据。
