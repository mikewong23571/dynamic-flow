# 规格：工作项进度总览与单项推进状态

## 背景与现状

用户使用 coding agent 作为推进业务的胶水，需要从整体看到 pending 工作项还剩多少、已完成多少，并能了解单个工作项当前推进到什么状态。

当前已实现：WorkItem 独立身份、open/completed 业务状态、由最新 Run 派生的五种展示状态、阶段/摘要/最近进展、完成条件与依据、等待与历史。工作项列表支持搜索、筛选、轮询；阶段和摘要由正式运行的显式里程碑更新。当前不足：

1. 列表只有总数，没有状态分布及未完成/已完成汇总。
2. 无运行的新项与运行成功但未结项的事项都可能显示“待推进”，缺少下一步解释。
3. 详情的阶段与执行事实未集中呈现，工作项视图不返回当前活动节点。
4. 业务阶段依赖预先配置的里程碑；没有独立的 Agent 进展报告入口，摘要也主要是定义中的固定文字。

反例：Agent 已完成资料分析、缺少版本范围，Run 成功结束，但未配置里程碑。用户回到列表只看到“待处理/待推进”，不知道已经取得成果，也不知道需要补什么。

依据：[工作项故事 H2/H3/H4/H10/H11](../../../docs/workitem-stories.md)、[当前设计](../../../docs/design.md)、[工作项服务](../../../src/server/work-items/index.ts)、[工作项页面](../../../src/client/features/work-items/WorkItems.tsx)。本文件记录本 track 的范围与合同；实际实现、验证结果与适用边界见 [验收记录](evidence.md)。

## 目标

- 整体：进入“工作项”即可看见未完成、已完成，以及未完成项的状态分布；点击数量定位相应事项。
- 单项：在详情首屏理解业务阶段、当前在做什么、最近报告的成果、等待/阻碍及下一步，不必先进入画布或阅读聊天。
- 反馈：正式执行中的 Agent 可提交结构化进展，保存后 HTTP 与页面可见，重开服务后仍存在。
- 可解释：区分运行事实、Agent 报告和用户确认；Run 完成、工具成功或 Agent 声称完成均不自动结项。

## 非目标

- 不建设可配置 dashboard、报表平台、趋势图、燃尽图、SLA、任务分配或通知系统。
- 不新增通用状态机、事件总线、进展插件协议、仓储层、独立服务、Agent loop 或前端状态框架。
- 不引入统一业务阶段模板、固定线性阶段序列、节点完成百分比或 LLM 猜测的业务完成率。
- 不把所有 Work/Run、材料条目或 invoke 调用自动转换成 WorkItem；未登记为工作项的执行不计入总览。
- 不变更显式结项、完成条件、持久等待、方法版本及旧运行不可变语义；报告阻碍不会自动暂停或唤醒 Run。
- 不新增全局工作项对话 Agent 或方法作者直接管理工作项的工具集。作者 Assistant 继续编辑方法。
- 不改默认启动落点，不迁移目录，不新建 worktree，不安装新依赖。

## 功能与最小合同

### 1. 统计与筛选

在现有“工作项”页头与列表之间放紧凑汇总，复用按钮/控件，不新增独立 dashboard 页面。

| 业务名称 | 统计口径 | 点击行为 |
| --- | --- | --- |
| 全部 | 全部已登记 WorkItem | 清除状态筛选 |
| 未完成（pending） | `item.status !== completed` | 查看所有未结项项，包含推进中、等待中与需处理 |
| 已完成 | `item.status === completed`，即现有“已结项” | 查看已结项项 |
| 待推进 / 推进中 / 等待中 / 需处理 | 分别对应 `effectiveStatus` 的 open/running/waiting/attention | 查看该展示状态的项 |

“已完成”与“已结项”同义，实际界面统一沿用“已结项”。必须满足：全部 = 未完成 + 已结项；未完成 = 四种未结项展示状态之和。

汇总固定统计全部工作项，不随搜索、状态筛选或客户端分页缩小；区域标明“全部工作项”，列表另显示当前匹配总数。点击汇总保留搜索词、回到第一页，选中态清楚；提供原有清除搜索方式。

扩展现有 `GET /api/items` 响应，在 `{items,total}` 上增加 `summary`，至少含全部/未完成/五种展示状态的数量。服务端先从同一批视图计算汇总再筛选，`total` 保持“当前匹配数”语义；新增 `status=pending` 过滤值，不新增持久化业务状态。详情、列表、汇总使用同一派生逻辑，不单独保存计数。

继续使用现有约两秒只读轮询；更新已有行不自动重排。零项显示 0；加载时不显示假的 0；读取失败保留上次内容并明确错误，不用旧数据伪装刷新成功。

### 2. 单项当前进展

现有详情首屏集中回答以下问题，列表保留简洁摘要；长证据、输出和运行日志继续按需查看。

| 用户问题 | 数据与呈现 |
| --- | --- |
| 业务推进到哪里 | 已记录的 `stage`，独立于执行状态 |
| 现在在做什么 | 从最新关联 Run 的活动节点及固定定义派生节点名称/责任；并行时允许多项，不伪装成唯一线性步骤 |
| 最近取得什么成果 | 已保存的 `summary`，标明 Agent 报告或里程碑来源及时间 |
| 为什么停在这里 | 真实等待原因/截止时间、执行错误，或明确报告的业务阻碍，分别标注来源 |
| 下一步是什么 | 明确报告的下一步；缺少报告时按实际执行/完成条件显示操作提示，不生成业务推断 |

扩展 WorkItem 的最少持久字段：可选 `nextAction`、`blocker`；沿用 `stage`、`summary`、`progressAt`，不新增独立 Progress 实体。新业务历史条目保存这次报告的阶段、摘要、下一步、阻碍与来源，不能只保留当前值而丢失历史内容。

`WorkItemView.execution` 可增加只读 `activeNodes` 摘要，基于固定 Run/Definition 以及已落盘的展开子图派生；复用已有子图读取/投影能力，不复制执行器。动态展开显示实际活动步骤，并保留原责任名称；所有并行活动都可查。

展示优先级：已结项 > 未决运行的真实运行/等待状态 > 失败、中断、取消 > 空闲且存在当前业务阻碍时的“需处理” > 待推进。Agent 报告不能掩盖真实运行失败或真实等待；阻碍仅是记录，不能冒充 RunWait。

成功但未结项显示明确次级提示：条件未全部确认时“本轮执行已结束，工作项尚未结项”；条件及依据齐全时“待结项确认”。它们不是新的业务状态，不因 Run 成功推断条件已满足。“已确认条件 1/3”是条件计数，不是业务进度百分比。

旧工作项无新增字段时正常读取，显示“尚未记录下一步/业务阻碍”；无 Run 显示“尚未执行”。活动节点变更和心跳不更新 `progressAt`。阶段和摘要可持续保留；历史运行的阻碍与下一步不能冒充新一轮当前指令：新运行、切换方法、重开时清除旧的这两项，里程碑取代报告时也清除未明确续用的两项，旧值留在历史。

### 3. Agent 进展报告

增加一个业务动作 `reportProgress`，由 work-items 服务在现有按工作项串行、原子文件保存路径内完成；通过现有 `POST /api/items/:id/actions` 暴露，并向正式工作项的普通执行 Agent 提供一个 `report_progress` 工具。应用入口注入直接回调，不让 assistant 绕过业务模块改文件，不建立通用工具注册平台。

最小输入：报告 ID、非空阶段和摘要、可选下一步/业务阻碍、可选本项材料引用。工具调用的工作项、workId/runId/definitionId/nodeId/instanceId 来源由服务端固定上下文绑定，不交给模型自行指定；使用 toolCallId 与执行身份构造可重试的报告 ID。

HTTP 直接调用时目标由 URL 固定，报告 ID 由调用方提供；运行来源可选。有运行来源时校验属于本项当前正式运行；无运行来源的外部记录只允许在没有未决运行时提交，使用工作项当前 revision 检查迟到覆盖，来源显示“外部报告”。这是直接动作接口，不建设外部 Agent 接入平台。

最小输出：保存后的 WorkItemView；页面下一次轮询可见，报告成功只表示已保存，不能表示业务事实已验证。

错误：字段不完整、材料不属于本项、来源不匹配、旧版本报告、工作项已结项、运行已停止/结束、相同报告 ID 不同内容、保存失败均明确拒绝。相同 ID 相同内容重试返回当前视图，不重复历史、不刷新业务进展时间；不新增去重数据库，复用历史条目 ID 和保存的报告内容。不同并行节点的报告都保留历史，当前摘要采用实际保存顺序，不推断阶段先后。

例如，工作项 CASE-01 的普通 Agent 在正式运行中提交：

```json
{
  "stage": "影响调查",
  "summary": "已整理现有公告，尚缺产品版本范围。",
  "nextAction": "补充产品版本清单后复核。",
  "blocker": "缺少产品版本清单",
  "materialIds": ["M01"]
}
```

工具成功后记录“Agent 报告”，关联当时的执行与材料；不会勾选完成条件、结项、停止当前运行或创建持久等待。没有真正 Wait 时不能显示“等待事件”。即使稍后节点输出校验失败，报告历史仍可查且明确是报告，当前执行失败必须可见，不把先前报告改称验证成功。

仅 workItem/full/commit 的普通执行 Agent 可报告，作者编辑、动态规划会话、试运行、比较和 preview 不提供写入工具；展开后的普通执行节点遵循同样约束。停止信号、已取消运行及旧 Run 的迟到工具调用不得写入。沿用现有中断语义，不宣称外部动作恰好一次。

保留显式里程碑路径；报告与里程碑复用工作项进展保存及来源记录，两者可共存。里程碑记录执行经过的阶段，Agent 报告记录模型声明的进展，用户确认仍负责完成条件与结项。工具说明要求在阶段成果、明确阻碍或下一步改变时报告，不写 token 心跳或每次文件读取日志。Agent 没有报告时如实显示缺失，不从聊天猜测。

## 验收条件

- **整体数量与定位**：10 项中待推进 2、推进中 3、等待中 1、需处理 2、已结项 2；显示全部 10、未完成 8、已结项 2。搜索、状态切换与翻页不改变全局汇总；每个入口筛选正确，零匹配时仍可切换汇总。
- **状态生命周期**：开始执行、等待、失败/中断、业务阻碍、结项、重开均使列表/详情/汇总一致；重开减少已结项、增加未完成，不创建新业务身份。
- **单项理解**：新项、本轮成功但未结项、待结项确认、有阻碍、等待事件、执行失败均可区分；单步骤、并行和动态展开显示真实当前活动，不用节点比例冒充业务完成。
- **无需预设里程碑**：无 milestone 的正式 Agent 流程调用报告工具后，阶段/摘要/下一步/阻碍在 HTTP 和页面可见，保存与重启后仍存在。
- **事实边界**：报告来源与材料可追溯；报告后节点失败时执行失败仍可见，报告不会变成用户确认；条件未满足不能结项，Run 成功不改变业务完成状态。
- **重复与迟到**：相同报告重试只记一次；相同 ID 不同内容、跨工作项材料、旧 Run、停止后和旧 revision 的迟到报告被拒绝；新一轮不沿用旧阻碍/下一步。
- **隔离与回归**：两个工作项共用方法而不串进度；作者、规划、单节点试验、候选比较和 preview 不写进展；原有里程碑、等待/恢复、结项/重开仍可用。
- **产品呈现**：1440×900 与 1024×768 实际浏览器操作和截图检查；含空/加载/错误、长摘要、筛选零匹配、轮询不重排行或丢阅读上下文。

验证结果必须区分模块测试、相邻模块真实文件/HTTP/运行联测、Pi 替身、真实模型、浏览器操作与用户视觉判断。具体通过范围与未测项见验收记录；模型不会报告或报告不准确时如实记录，不补固定业务答案冒充闭环。

## 用户验收指正（2026-10-21）

用户指出当前侧栏“已打开的流水线”条目出现突出白色边框，末尾关闭符号显得突兀。此前两尺寸工作项截图的侧栏未打开流水线，未覆盖该状态。增加实际存在打开项（含长标题、多项、选中项）的侧栏检查，修正有证据的样式/交互层级问题，保留工作项功能与已打开入口的状态语义；不以空侧栏截图声称该情境已验证。

已复现原因：WorkItems.css 引入的 components 层在 main.tsx 的全局 styles.css 之前注册，导致 base 层优先级覆盖业务组件。实测条目变成 13px/白字/1px 边框；只调整全局样式导入顺序即可恢复 12px/灰字/无边框。最小修正入口是 main.tsx，避免用更强侧栏选择器掩盖全局层次错误。

样式恢复后用户继续反馈条目字体偏薄、不协调：仅调整已打开流水线名称的字重，与相邻导航协调，保留灰字/无边框及柔和选中态；用两尺寸实际截图复核，不扩大为全站字体改造。
