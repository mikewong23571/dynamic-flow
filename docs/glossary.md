# 术语与编号

本页解释本项目文档的用词，不要求用户先学习软件术语才能操作产品。文档首次出现缩写应就地解释；模块验收先写业务名称，再附编号。

## 阅读编号

| 写法           | 含义                                                                                                | 到哪里找具体内容                                   |
| -------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| A–F、A1、B3 等 | 六类用户目标及其故事编号：A 开始工作、B 理解/修改、C 执行/控制、D 检查结果、E 试验改进、F 采用/续做 | [用户故事](./user-stories.md)                      |
| T1–T8          | 八条完整用户验收路线的项目内编号，例如 T1 是“从目标到报告”                                          | [验收路线](./user-stories.md#3-最终怎样验收)       |
| P01–P32        | 具体行为/边界测试场景的项目内编号，例如 P29 是“Pi 工具实改画布”                                     | [场景清单](../spike/tests/cases.md)                |
| H1–H11         | 持续业务工作项的十一条故事，涵盖身份、管理、等待、恢复和结项                                        | [生命周期故事](./workitem-stories.md)              |
| L1–L5          | 本轮五条跨模块生命周期路线，区别于早期短流程 T1–T8                                                  | [生命周期路线](./workitem-stories.md#产品验收路线) |
| F01–F04        | 验收材料里的客户反馈样本编号；不是 F 类用户故事                                                     | [验收材料](../spike/tests/fixtures.md)             |

T、P 是这里使用的索引前缀，不是通用行业缩写；旧文档没有给它们解释清楚。一个用户故事可以对应多个场景，一个验收路线也会连接多个故事。看到编号不代表实现或验收通过。

## 技术缩写

| 缩写     | 英文全称                          | 本项目中的含义                                                             |
| -------- | --------------------------------- | -------------------------------------------------------------------------- |
| IR       | Intermediate Representation       | 中间表示；本应用可保存、编辑、执行的工作流定义，包含节点、参数和连接       |
| JS       | JavaScript                        | 保存受约束的工作流定义和编写普通处理函数所用的语言                         |
| TS       | TypeScript                        | 在 JavaScript 上增加类型检查；本应用源码语言                               |
| TSX      | TypeScript with JSX syntax        | TypeScript 中描述 React 界面的文件语法                                     |
| UI       | User Interface                    | 用户界面，即画布、表单、结果与对话等操作部分                               |
| LLM      | Large Language Model              | 大语言模型；通过配置的协议、地址、模型名和密钥调用                         |
| SDK      | Software Development Kit          | 软件开发工具包；这里主要指 Pi 提供的会话、工具调用、模型和事件能力         |
| API      | Application Programming Interface | 程序接口；两个模块或前后端约定怎样请求操作和取得结果                       |
| HTTP     | Hypertext Transfer Protocol       | 浏览器与后端发送请求和响应所用的协议                                       |
| SSE      | Server-Sent Events                | 服务器发送事件；让后端持续把工作状态和执行活动推给浏览器                   |
| JSON     | JavaScript Object Notation        | 一种文本数据格式；本地工作元数据等使用它保存                               |
| ID       | Identifier                        | 标识符；用于找到具体工作、定义、运行、节点或结果，不是给用户阅读的业务名称 |
| IO / I/O | Input/Output                      | 输入/输出；文件 IO 指实际读写本地文件                                      |

下列术语主要出现在“暂不建设”的说明中：AST = Abstract Syntax Tree（抽象语法树）；DSL = Domain-Specific Language（领域专用语言）；DTO = Data Transfer Object（数据传输对象）；CRUD = Create/Read/Update/Delete（增删改查）；ORM = Object-Relational Mapping（对象关系映射）；SLA = Service-Level Agreement（服务水平约定）；REST = Representational State Transfer（一种组织网络接口的架构风格）。不必为了原型先实现它们对应的框架。

## 产品对象与运行概念

| 用词                               | 在这里表示什么                                               | 容易混淆的区别                                                            |
| ---------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------- |
| Work / 方法工作区                  | 一套处理方法的目标说明、样例材料、定义与编辑/运行记录        | 保留历史字段名；不等于长期业务工作项                                      |
| WorkItem / 业务工作项              | 有稳定业务编号、目标、独立证据、条件依据、阶段和历史的一件事 | 可以使用不同方法经历多次 Run，结项不由节点完成计数决定                    |
| Definition / 定义                  | 某一版节点、任务、参数、连接和输出规则                       | 画布和执行使用同一份定义，不维护两份各自变化的逻辑                        |
| Draft / 草稿                       | 当前准备修改的定义，由 draftId 指向                          | 草稿不是已经运行的结果                                                    |
| Candidate / 候选                   | 准备与当前采用做法比较的草稿                                 | 首版是草稿的用途，不另建一种定义系统                                      |
| draftBaseId / 草稿起点             | 用户明确选来开始本次改进的定义版本                           | 继续已有草稿不重置；默认作为比较基线，不一定等于当前采用版                |
| Adopted / 已采用                   | 默认用于后续运行的那版做法，由 adoptedId 指向                | 采用做法不等于保留全部试验产物                                            |
| Run / 一次执行                     | 固定定义、输入和工作项修订的执行记录，包含实例、等待和事件   | 编辑方法不改变旧 Run；等待/恢复可以继续同一个 Run                         |
| 一件事 / 直接输入调用（invoke）    | 不经过材料选择，把裸值直接交给现成做法跑一次；入口按钮叫「直接输入」 | 概念名挂在未来首页卡片上；界面按钮保持白描「直接输入」，不靠隐喻命名      |
| Node / 节点                        | 画布上一个可理解、可调整的步骤                               | 同一步处理三条材料仍是一个节点                                            |
| Instance / 执行实例                | 某次运行中，节点针对一条输入或一组输入的一次执行             | 三条材料逐项处理可以产生三个实例                                          |
| Port / 端口                        | 节点输入或输出的具名位置，例如 input、match、rest            | 连线决定数据从哪个输出到哪个输入                                          |
| operation / 组合运算               | map 单项转换、flatMap 展开一层、aggregate 整批一次调用       | map 返回数组不自动展开；aggregate 不是满足结合律的 reduce                 |
| each / all                         | 旧定义的逐项 / 整组模式                                      | 继续适配；新定义使用 operation 明确语义                                   |
| inputSchema / expectedOutput       | 单次调用输入与返回值的 JSON Schema                           | 不等于完整端口类型推导；实际值由 Ajv 检查                                 |
| Wait / 持久等待                    | 保存事件、原因和截止时间，收到消息或到期后继续               | 释放执行资源；不是内存中挂一个长函数                                      |
| Milestone / 业务里程碑             | 显式记录工作项阶段、摘要与输入来源的节点                     | 仅正式 full/commit 生效；不自动结项                                       |
| commit / preview                   | 正式业务推进 / 无业务提交的试验                              | preview 不写工作项，等待输出也标明为预览                                  |
| resume / 恢复                      | 显式继续被中断 Run，保留成功实例                             | 不等于新 Run 重试，不恢复任意函数栈                                       |
| signal / 外部事件                  | 带事件 ID、名称、payload 和接收时间的消息                    | 匹配等待才唤醒，重复相同消息不重复推进                                    |
| Runtime / 运行时                   | 按定义调用节点并记录进展的执行代码                           | Pi 负责 Agent 节点的模型/工具循环，应用负责节点依赖、有限并发、等待和数据 |
| Tool call / 工具调用               | 模型请求执行一个已注册函数，例如 update_flow                 | 一段“已修改”的回复不能替代函数实际保存                                    |
| Snapshot / 快照                    | 在某一时刻固定的数据内容，或发给前端的一份完整当前状态       | 只发送定义 ID 而没有定义内容，前端不能据此构图                            |
| Fixture / 测试样本                 | 固定输入或可控测试数据/行为                                  | 能复现测试，不代表真实模型已验证                                          |
| Mock / 测试替身                    | 为某个测试临时替代真实依赖的对象或函数                       | 模块互相 mock 不能证明实际连接成立                                        |
| Faux provider                      | Pi 实验里使用的可控模拟模型提供者                            | 真实 SDK 执行了工具，但回答不是来自用户配置的真实模型                     |
| Spike / 技术验证实验               | 用小例子检验方案或接入摩擦                                   | 本仓库 spike 是伪代码推演，examples/component-spike 是历史可运行实验      |
| Pi、React Flow、assistant-ui、Hono | 工具或库的产品名称                                           | 不是本项目自定义缩写；职责见依赖说明                                      |
| Conductor / track                  | 项目工作记录方式 / 一轮有范围的任务记录                      | 一个 track 完成不等于整个产品完成                                         |
| AGENTS.md                          | 放在目录里的 coding agent 工作约定文件                       | 说明职责与约束，不是应用运行配置                                          |

## 文档的四项组织原则

- **重复**：同类模块重复相同标题和说明顺序；同一个业务概念保持同一个名称。详细规则只维护一份，引用时保留简明上下文。
- **对齐**：目标、接口、负责模块、验收条件彼此对应；状态词和字段含义在前后端一致。表格同列使用同类信息。
- **对比**：清楚区分已实现/计划、目标/非目标、已验证事实/假设、真实模型/测试替身。
- **亲密**：把相关说明放近：缩写旁给解释，编号旁给场景名，模块职责旁给依赖与验收，接口旁给输入输出和例子。不要让读者为了理解一行文字跳转多份文档。

这些原则不意味着忽略基本工程实践：明确接口、职责分离、共享类型、错误处理、必要复用与测试都是起点。避免的是无现实需求的通用平台与昂贵抽象。

本轮管理与函数式验收编号：M1–M3 为管理体验故事，FP1–FP3 为纯函数变换故事，完整定义见 [track 规格](../conductor/tracks/functional-ir-management_20260920/spec.md)。pipe 是从左到右组合；reduce 是有初值的顺序归约；pattern 是用于匹配和解构的数据形状；rest 是解构后剩余字段/元素，均不是外部服务或模块名。

本轮组合故事 C1–C4 仅在 [多路组合 track](../conductor/tracks/multi-input_20260920/spec.md) 内编号：merge 是按端口顺序拼接，collect 是保留名称的数组对象，join 是按键配对。inner/left/right/full 分别为内/左/右/全连接，缺配侧为 null；详细边界见 [集合语义](multi-input.md)。
