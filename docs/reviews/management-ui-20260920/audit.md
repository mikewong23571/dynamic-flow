# 工作项与流水线管理 UI 审计

2026-09-20，审计基线 `6b2df81`。本轮为审计，未修改产品实现。

检查了运行中的 1440×900 工作项/流水线列表、1024×768 流水线列表、标签页键盘行为，以及正式源码、旧 Spike、shadcn 配置。当前可见样本为1个已结项工作项、3条未归档流水线；没有据此宣称多状态或大量条目的视觉验收通过。

## 结论

问题在信息组织、交互模式和组件落地。暗色、Geist 字体、边框与圆角已经统一了一部分外观，但管理页面没有形成完整的条目展示体系。前次功能路线通过不能覆盖此次设计反馈。

正式应用确实没有系统接入 shadcn/ui：旧 Spike 的组件、工具函数和配置没有迁入正式入口，正式源码另写了一套基础控件。不是 shadcn 无法支持本产品，也不能以“原型避免抽象”为理由解释这部分重复。

## 优先修正的问题

### 1. 高：流水线身份与状态命名失真

实际方法列表仍标题为“所有工作”，创建入口叫“新建工作”，旁边又有“工作项”。“进行中”标签实际筛选条件只是 archived=false，并不代表正在执行。用户必须猜测两个工作入口的区别。

证据：`src/client/WorkLibrary.tsx:94` 标题、`:110` 标签；`src/client/Sidebar.tsx` 导航。截图 [流水线1440](flows-1440.png)。

建议：用户可见名称统一“工作项 / 流水线”；流水线归档维度使用“全部 / 已归档”或“未归档 / 已归档”，定义状态与执行状态分别表达。此问题优先于配色微调。

### 2. 高：shadcn 仅留在实验中，手写交互已经丢行为

`components.json:8` 的 CSS 仍指向 examples/component-spike；根 tsconfig 的 @ 别名也指向 Spike，正式 tsconfig 改成 src，正式 Vite 没配置相应别名。继续在根目录直接执行组件生成命令，不能假定会得到可用的正式组件路径。

`src/client/components/ui.tsx:5` 的 Button 仅拼接 CSS 类；Badge 自写，Modal 使用 Radix Dialog。这说明已做少量复用，不能说“完全没有组件”，但不是已经完整接入 shadcn。

Input / Textarea / Select / Checkbox / Tabs / Table / Pagination 仍由各页面直接拼装；正式 src 没有使用旧 Spike 的 cva、cn 与 TanStack Table。`styles.css:43` 和 `:95` 两组全局控件规则也有重叠，页面继续写覆盖样式。

实际在“进行中”标签聚焦后按 ArrowRight，焦点及选中项均不变化。手写 role=tab 没有实现成套 Tabs 键盘行为。复用应包括交互约定，不能只复用颜色和按钮外框。

### 3. 中：工作项行没有主次，重复字段挤占信息预算

已结项行同时出现状态 Badge“已结项”、阶段“已结项”、摘要“所有完成条件已确认并记录依据”，旁边又有“执行完成”。业务状态与执行状态必须保留区别，但不必每项都以相近权重同时展示。

`WorkItems.tsx:187` 总是连续渲染状态、阶段和摘要，`:199` 再渲染执行状态；标题 `:179` 先编号后名称。宽度26%/30%/24%/15%/5%、顶部对齐和不限行摘要在 `WorkItems.css:49` 起。

建议：名称作为行的主锚点，编号作为次信息；状态与阶段相同则不重复；业务进展保留一条有区别的摘要；等待原因与截止时间紧邻呈现。执行详情降为次信息，但运行失败/中断必须突出。主标题进入详情，右侧只保留必要行操作，避免两个同等入口。

截图：[工作项1440](items-1440.png)。空白本身不是缺陷，不能靠添加说明或卡片填满屏幕。

### 4. 中：流水线展示了作者指令，却缺少维护时需要比较的信息

每条使用文件夹图标、名称、两行完整目标、更新时间、常驻“重命名/归档”。样例直接展示“先用一个Agent……只需这四个节点……”等作者指令。第一条比第二条更高，时间随正文变化，没有稳定扫描轴；1024时次要动作又竖向堆叠。

证据：`WorkLibrary.tsx:193` 直接显示 work.goal，`:210` 常驻操作；`WorkLibrary.css:115` 两行正文，`:197` 窄屏动作纵排。截图：[1440](flows-1440.png)、[1024](flows-1024.png)。

建议：紧凑行或表格，核心为“名称及一行用途 / 定义状态 / 最近修改 / 更多操作”。采用状态或草稿状态比完整作者指令更适合方法管理；必要摘要从当前定义记录提供，不能伪造未接入的数据。重命名/归档进入 DropdownMenu，打开编辑器保留为明确主操作。

### 5. 中：两个管理页面缺乏重复、一致的组织规则

流水线搜索在右侧，需要提交；工作项搜索在左侧，每次输入即发请求。流水线有分页，工作项无分页。标题内边距34/32、字重650/600、背景paper/canvas也分别定义。

不同业务允许列不同，但搜索行为、工具栏位置、标题间距、空态、加载态、分页与行操作应统一。否则用户在两个相邻管理页面间需要重新学习。

### 6. 中：列表会随轮询重新排序，规模适配还没验证

工作项每2秒取全部列表，服务端按 progressAt 排序；其他事项有业务进展时可能换行位置。缺少分页/排序控制，长摘要没有行数约束。当前只有一行完成项的截图不能证明管理视角的多事项可扫读。

这属于代码推导出的风险，本轮没有构造几十条多状态记录来假称复现。后续验收应使用至少12条不同状态、长短名称与摘要，并检查阅读中的更新行为。

## 按四条设计原则调整

| 原则 | 当前偏差                                                   | 应采用的规则                                             |
| ---- | ---------------------------------------------------------- | -------------------------------------------------------- |
| 重复 | 页头、搜索、标签、分页和操作各写一套；同一行又重复状态文字 | 重复布局和控件语法；去掉没有新增信息的文字重复           |
| 对齐 | 日期跟在变长目标后，长短行缺少稳定扫描轴                   | 标题、状态、时间、行操作共享列轴和间距                   |
| 对比 | 长目标/次要操作抢占空间，业务进展和执行状态没有主次        | 名称第一，阶段/异常第二，编号/时间第三；颜色集中表达状态 |
| 亲密 | 状态、阶段、摘要逐块叠加，待办原因和时间关系不突出         | 名称与编号一组；阶段与摘要一组；等待原因与期限一组       |

## shadcn 应如何落地

shadcn/ui 提供可纳入仓库并修改的组件源码和组合接口，不是仅安装一个 npm 包即可使用的黑盒。组件源码留在项目中是正常做法；问题是目前正式应用重新实现了基础控件，没有继承已选组件的接口和交互。参考 [官方说明](https://ui.shadcn.com/docs)。

建议继续选 Radix 这一组 shadcn 组件，复用已有底层，统一组件目录、路径别名、Tailwind 入口及主题 tokens；默认暗色可以保留。基础 Button/Input/Textarea/Select/Checkbox/Badge/Dialog/Tabs/DropdownMenu/Table/Pagination/Skeleton/Empty 按实际页面需要接入。主题调整通过 tokens 和 variants 完成，逐步删除旧全局控件规则。

业务层只提取两页确实重复的 PageHeader、列表工具栏、状态标签、行菜单和分页组合。列内容、业务动作及 HTTP 数据仍属于各自页面。不需要通用 CRUD 配置平台，也不用把整个项目改成一个巨大 DataTable。

[官方 Data Table](https://ui.shadcn.com/docs/components/radix/data-table) 提供表格组合路径。项目已有 TanStack Table 9.2.4，旧 Spike 使用 useTable/tableFeatures；迁移时核对锁定版本，不能照搬其它版本示例。只需静态显示时先用 Table；排序/分页需要才接表格状态能力。

## 改造顺序与验收

1. 先统一“工作项 / 流水线”的术语与状态维度，确定每种行保留哪些信息。
2. 把 shadcn 正式接线，统一控件与主题；验证路径、样式、键盘及焦点，再替换两页手写控件。
3. 共享管理页布局，分别实现两种业务行；清理被替代的 CSS，而不是新增覆盖层。
4. 回归现有创建、搜索、归档、分页、事件、结项路线，并增加列表质量验收：至少12条混合状态；名称一眼可辨；同义状态不重复；等待与异常可定位；1440/1024无布局冲突；Tab/箭头键/Enter/Escape可用；轮询不抢焦点、不覆盖搜索或未保存输入。

功能测试与上述视觉/交互标准分别验收。当前这份报告没有将建议描述为已经实现。
