# 用户故事与原型验收

状态：讨论稿，2026-09-20。用于与用户确定最终验收范围，尚未代表用户批准或功能实现。基于 [当前设计](./design.md)，不在本轮展开组件、接口或实现任务。

## 1. 分类与使用方式

以“独立完成一项工作的用户”为主要角色。用户不需要会编程；同一个人可能先提出目标，再调整做法、检查结果。不为原型预设管理员、审核员等额外角色。

层级为：**用户目标类别 → 用户故事 → 验收场景 → 实际证据**。类别描述用户想完成什么；故事描述具体价值；验收场景描述可以实际操作并判断成败的路径。画布、Chat、IR、runtime 是实现手段，不作为上层分类。

| 类别 | 用户要回答的问题 | 首版故事 |
| --- | --- | --- |
| A 开始一项工作 | 我要做什么，用哪些材料，准备得到什么？ | A1 提供目标与材料；A2 得到可理解的初始做法 |
| B 理解与修改做法 | 准备怎样做，我如何调整？ | B1 看懂流程；B2 手动修改；B3 对话修改；B4 发现不可运行的配置 |
| C 执行与控制 | 做到哪里了，我能否停止或处理失败？ | C1 执行与进度；C2 停止；C3 失败后局部重试 |
| D 检查与判断结果 | 结果是什么，依据是什么，问题在哪里？ | D1 检查节点与样本；D2 阅读最终产物 |
| E 小范围试验改进 | 改法是否更好，是否值得采用？ | E1 提出候选；E2 样本试运行；E3 同输入比较；E4 识别过期比较 |
| F 采用、续做与复用 | 留下什么，下次怎样继续？ | F1 采用做法；F2 保留结果并续做；F3 换材料复用；F4 重新打开工作 |

以下 19 个故事建议作为首版必验候选；第 4 节的扩展故事不进入首版。这里的“必验”是范围建议，不表示已经验收通过。无需为每个故事建设独立页面或子系统。

## 2. 首版用户故事及验收条件

### A 开始一项工作

**A1 提供目标与材料**

作为用户，我希望给出工作目标并提供材料，以便应用围绕我的真实输入开展工作。

- 从空工作区创建任务，输入“整理客户反馈，区分问题、需求与称赞，给出有依据的建议”。
- 首版至少支持粘贴多条文本并确认拆分结果；能查看每条材料的内容和数量。无需同时支持上传、网盘和网页抓取。
- 缺少目标或材料时，明确指出缺什么并保留已输入内容；可以补齐后继续。

**A2 得到可理解的初始做法**

作为用户，我希望描述目标后得到一套可以检查和调整的流程，以便不从空白画布手工搭建全部步骤。

- 根据本次目标与材料生成至少包含“分类反馈 → 汇总建议”的可运行草稿，并在画布展示节点和连接。
- 节点名称、任务与最终输出对应当前目标；不是每次都展示固定示例图。验收时补充“报告必须引用反馈编号”，要求应落入相关节点配置。
- 可以在运行前查看和修改草稿；生成失败时看得到原因并可重试，不显示假的成功流程。

### B 理解与修改做法

**B1 看懂步骤与数据去向**

作为用户，我希望从画布理解步骤、依赖和条件，以便判断应用准备怎样完成工作。

- 不打开源码，能够指出材料从哪里进入、哪些步骤逐条处理、哪里汇总、结果从哪里输出。
- 选择节点能看到任务、输入来源和输出去向；条件分流能看出两条连接分别代表什么。
- 增加材料数量不会把同一个步骤复制成大量画布节点；运行实例在需要时展开查看。

**B2 通过画布和配置直接修改**

作为用户，我希望拖放节点、调整连线和配置，以便把流程改成我需要的做法。

- 可以添加、删除节点和连接，修改任务与参数；例如在分类与汇总之间插入一个已有的普通处理步骤。
- 再运行时，实际输入与处理顺序遵循修改后的连接。只拖动节点位置不改变执行结果和已有比较的有效性。
- 更改字段条件后，输入走向对应分支；其中一支没有材料时，整个流程仍能完成汇总。
- 全程无需编辑 JS，也无需手工改文件。

**B3 在上下文中通过对话修改**

作为用户，我希望选中节点后直接描述改法，以便不用自己找到所有配置字段。

- 选中“分类反馈”并提出“同时表达赞扬和问题时，归为问题，并保留两方面依据”；Assistant 明确本轮针对哪个节点。
- 修改实际落到同一个草稿，画布与配置面板随之更新；能看见改变的节点、参数或连接。
- 不相关步骤保持原样；仅回复“已修改”而定义未变化不算通过。无法完成时明确说明，保留可继续编辑的草稿。
- 发送后切换选择，不把正在处理的请求悄悄改成另一个节点。

**B4 知道流程哪里不能运行并修正**

作为用户，我希望在接错线或缺少配置时得到局部提示，以便自己修复流程。

- 必填输入缺失、端口不匹配或不支持的回连，提示指向具体节点或连接并说明如何处理。
- 不完整草稿允许保留和编辑，但不能被冒充为成功启动的运行。
- 修正后可以运行；正常编辑过程不因频繁弹窗而中断。

### C 执行与控制

**C1 运行并掌握进度**

作为用户，我希望启动流程并看到真实进展，以便知道正在处理什么、还剩多少。

- 运行明确绑定本次做法和输入；逐项处理能显示总数、完成数，并展开到具体材料。
- 可以区分尚未开始、运行中、已完成、失败和已取消；结果出现后可以立即查看。
- 运行期间编辑草稿，不改变已经启动的这一轮；界面能区分当前运行与待运行的修改。

**C2 停止不值得继续的运行**

作为用户，我希望随时停止，以便避免继续执行不合适的做法。

- 在节点执行中停止，界面先显示停止处理中，收到实际停止结果后显示已停止；停止后不再启动后续步骤。
- 已完成结果仍可检查；取消不被标成全部成功。不能只停止页面动画、后台继续执行。

**C3 找到失败并只重试必要部分**

作为用户，我希望知道哪条材料在哪一步失败，并修正后局部重试，以便不重复全部工作。

- 用可控失败验证：失败节点、输入、原因和可执行的下一步能找到；已有成功结果保留。
- 依赖失败结果的步骤不会使用缺失数据继续伪造成功。
- 可以选择失败输入重新运行该节点，得到一条新运行记录；不会无提示地重跑已完成材料。后续续做使用 F2 的显式结果选择。

### D 检查与判断结果

**D1 从结果回到输入与处理步骤**

作为用户，我希望检查某条结果用了什么材料、经过什么处理，以便判断错误出在哪里。

- 从节点打开某条样本，能并看原始输入、实际输出以及所属运行；能看出这是哪一版做法的结果。
- 对混合反馈的错误分类，可以回到对应节点提出修改；无需在 Chat 历史中搜索或先理解内部 ID。
- 长内容、失败内容和部分完成内容都能阅读；切换节点再返回不会丢失当前试验的样本选择。

**D2 取得可用的最终产物**

作为用户，我希望读取和带走最终报告，以便工作结果能够用于实际任务。

- 报告能够完整阅读并复制正文，引用能对应本次真实输入；首版不要求 PDF、Word 或专门导出系统。
- 报告满足本次明确要求：包含分类结论、建议及材料依据，不把未提供的事实当成已知事实。
- 部分结果不能冒充完整报告；能看出其材料范围和所属运行。模型质量按要求和证据判断，不要求每次生成完全相同的措辞。

### E 小范围试验改进

**E1 从具体问题提出候选改法**

作为用户，我希望围绕不满意的结果调整对应步骤，以便明确这次试验想解决什么。

- 保留当前采用的做法，从问题样本进入对应节点的候选草稿，可手动或通过对话修改。
- 能区分当前做法与候选，看见改动范围；候选尚未采用时不替换默认做法。
- 候选中的节点增删、连线和参数变化可读，不依赖代码 Diff 理解。

**E2 只用少量样本试运行一个节点**

作为用户，我希望先选少量样本验证修改，以便避免每次重新执行整条流程。

- 选定一个节点和两条材料，试运行实际只处理这两条输入；不会自动重跑全量和所有上游。
- 缺少该节点输入时，允许选择已有结果、补充材料或明确执行上游，不偷偷恢复未知上下文。
- 运行开始后再改列表筛选或选择，不改变这一轮固定的输入。多节点片段试验放在后续。

**E3 用同样材料比较当前与候选**

作为用户，我希望并排比较两种做法的结果，以便判断改动是否解决问题、是否带来退步。

- 两侧使用同一组明确输入，按样本对齐，展示相关输出、失败和做法变化。
- 一条混合反馈用于检查问题是否修复，另一条单纯称赞用于检查是否被误伤。
- 历史结果只有输入和做法匹配时才可作为本轮基线，否则重新运行；不能拿不同样本的结果制造“变好”的结论。
- 不要求自动打分或评测平台；用户能根据约定的要求作判断即可。

**E4 避免用旧比较判断新修改**

作为用户，我希望知道比较是否仍适用于当前候选，以便不根据过期结果作决定。

- 试验后再改变节点任务、参数、连接或试验输入，旧比较明确标为需重新试运行。
- 原结果仍可检查；未试验的修改不显示为已验证。重新试验后，新的结果对应新的候选。
- 只移动画布位置、缩放或改变列表排序不会让语义未变的比较过期。

### F 采用、续做与复用

**F1 采用满意的做法**

作为用户，我希望把候选设为后续默认做法，以便后面的任务使用这次改进。

- 采用后，新运行使用该候选；以前运行的做法与结果不被改写。
- 放弃候选后，当前采用的做法仍可使用。
- 采用做法不会自动把候选的所有试验产物当作正式结果，也不声称未经试验的版本已验证。

**F2 保留满意结果并继续工作**

作为用户，我希望保留有用的旧、新结果并指定后续步骤的输入，以便不因为改了方法就丢弃已经完成的工作。

- 不采用候选，也能保留其某条满意产物；采用候选，也可以不保留其试验产物。两种操作不会互相代替。
- 选定旧运行的两条结果和候选运行的一条结果，明确确认作为汇总输入，再生成一份新报告。
- 汇总只使用所选结果；同一材料有多个版本时显示清楚并让用户作选择，不能无提示重复计算。保留来源，不要求用户手动去文件目录拼接。

**F3 使用同一做法处理新材料**

作为用户，我希望换一批材料再次运行已有做法，以便不用每次重建流程。

- 在当前工作内使用已采用做法，选择新材料创建新运行；不要求模板市场或跨项目发布。
- 节点逻辑保留，新报告引用新材料；旧报告和旧输入仍可查看，不混入新一轮结果。

**F4 重新打开后继续工作**

作为用户，我希望关闭再打开工作仍能找到之前的内容，以便分多次完成任务。

- 完成一次保存后，刷新或正常重启应用，目标、材料、采用版本、候选、画布位置和已保存结果仍可查看。
- 能识别历史比较是否仍适用，并继续编辑、试运行或用已有结果续做。
- 不要求进程崩溃后恢复正在执行的调用；中断的运行不得冒充仍在正常执行或已经成功。

## 3. 最终怎样验收

### 一套小而真实的材料

主场景为“客户反馈分析”，先使用 3 条固定材料，可由用户替换为真实材料：

| 编号 | 材料 | 用途 |
| --- | --- | --- |
| F01 | 界面很顺手，但导出报告经常失败，影响交付。 | 混合反馈；要求修改后归为问题，并保留正反两方面依据 |
| F02 | 希望支持批量导出，逐条操作太慢。 | 需求；也用于条件分流 |
| F03 | 搜索比以前快很多，团队很满意。 | 单纯称赞；检查改法没有误伤 |

额外一条“筛选后页码错乱，希望尽快修复”用于新材料复用。初次模型未误判 F01 时，不为了演示伪造错误；可以先设置一个明确较弱的分类要求，或围绕遗漏依据提出改进，并记录初始条件。

### 八条可操作的验收路线

| 路线 | 实际操作 | 覆盖故事 | 完成证据 |
| --- | --- | --- | --- |
| T1 从目标到报告 | 新建工作、粘贴材料、生成流程、检查步骤、运行、阅读并复制报告 | A1、A2、B1、C1、D1、D2 | 真实输入、画布、节点结果、带材料引用的报告 |
| T2 手工改变流程 | 插入/删除节点、调整连线、修改条件；制造一次无效连接并修正；再执行一次空分支案例 | B2、B4 | 操作后实际数据路径变化；错误可修；空分支能结束；移动位置不改语义 |
| T3 对话修改并做样本比较 | 选中分类节点、描述改法、固定两条样本、运行当前与候选、判断修复与退步 | B3、E1、E2、E3 | 定义真实改变，两侧同输入、同样本对齐，未运行其余材料 |
| T4 不混淆版本与上下文 | 发送修改请求后换选中节点；试运行后再次改任务或样本；运行中编辑下一版 | B3、C1、E4 | 请求目标固定、运行版本固定、旧比较过期；仅移动位置不使比较过期 |
| T5 独立采用与保留 | 分别尝试“只采用做法”和“只保留结果”；放弃一次候选；选择旧新结果生成报告 | F1、F2 | 默认做法和产物选择各自正确；新报告只用指定结果；历史保持原样 |
| T6 停止和失败后续做 | 一轮在运行中停止；另一轮注入单样本失败，查看原因、修正、只重试该输入 | C2、C3 | 真实取消/失败事件，已完成结果保留，后续未错误执行，新重试记录 |
| T7 换材料并重新打开 | 新材料使用已采用流程执行，保存、刷新并正常重启，查看历史和候选再继续 | F3、F4 | 新旧输入和产物可区分；保存内容恢复；未完成运行状态如实显示 |
| T8 完整工作区体验 | 在代表性工作区走完 T1、T3、T5，观察长文本、部分完成、错误和较窄窗口 | 全部故事的可用性 | 界面操作录像/截图与实际用户反馈；逐项记录体验问题及处理结果 |

T1–T7 判断业务行为是否正确；T8 判断用户能否理解并顺畅完成这些行为。组件安装成功、截图好看、测试全绿，均不能单独代表故事验收通过。

### 通用体验要求

- 用户能识别当前工作、选中节点、正在运行的版本、候选与历史结果，知道接下来主要能做什么。
- 画布、节点配置、结果与对话保留共同上下文；不强迫用户反复在脱节页面间搬运内容。
- 核心路径无需读源码、编辑 JSON、使用终端或让开发者现场改数据。
- 主要动作能直接找到；标签、状态与控件含义一致，正文可读，长结果可检查。至少在 1440×900 与 1024×768 桌面窗口检查布局；不因此扩展到移动端设计。
- 空、加载、运行、部分完成、失败、取消状态完整；错误说明指出可行动的下一步。
- 在真实代表性页面上统一字体、间距、密度、色彩和控件，用户确认视觉方向；不能以旧 Spike 外观或自动测试代替这一项。

### 证据与通过规则

每条路线执行后记录：使用的构建/提交、输入、操作、预期、实际、截图或运行记录、结论。状态使用“未实现 / 待验收 / 通过 / 未通过”；本文件当前所有路线均为未验收，旧组件 Spike 不计入新产品验收。

确定性 fixture 可用于稳定验证故障、取消、分支及版本状态；T1、T3、T5 还必须使用真实模型完成，证明流程生成、修改与节点工作确实成立。记录模型与原始输出；外部模型不可用时保持待验收，不把 fixture 成功当成真实闭环通过。

首版通过标准建议为：19 个故事的验收条件均有证据，T1–T8 全部通过；不遗留阻断核心路径、结果来源错误或版本混淆的问题。先讨论本稿范围，再用故事编号安排实现，不能把“文档写完”标为“产品通过”。

## 4. 后续故事与明确排除

| 后续故事 | 用户价值 | 延后原因 |
| --- | --- | --- |
| 选中多个连通节点做局部试验 | 一次验证跨步骤改动 | 首版先验证单节点试验与显式续做 |
| 按需查看只读 JS 定义 | 理解或向 coding agent 描述更深层实现 | 不阻断核心用户路径 |
| 保存跨工作的流程模板 | 多项工作复用同一做法 | 首版在同一工作内换材料即可 |
| 扩展文件导入与专用导出格式 | 更方便地使用现有资料和交付产物 | 首版先用文本材料与可复制报告闭环 |

安全、权限、隔离、多人协作、节点市场、任意代码编辑、无限循环、任意断点恢复、自动优化/评测平台不进入本轮用户故事或验收范围。

## 5. 本轮需要对齐的产品判断

本稿建议先用一个完整业务场景验收产品，再逐步扩展场景；客户反馈是验收材料，不是产品只能处理的业务。分类、流程理解、修改、试验和采用等能力应保持通用。

讨论时先确定六个上层类别是否覆盖用户工作，再决定各类哪些故事属于首版，最后锁定真实验收材料和输出要求。暂不把未确认故事直接转换成组件清单或大规模开发计划。
