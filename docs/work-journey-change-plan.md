# 对齐工作主线的应用改动路径

实施落点：[工作主线 track](../conductor/tracks/feature-work-journey_20261022/index.md)。充分调研后，首版正式局部续做收敛为明确的静态普通单步骤，沿用现有 node scope；多步骤选择完整方法，不引入任意子图续跑。具体范围以该 track 的 spec 与页面验收故事为准，本文保留总体路径背景。

2026-10-22。状态：改造计划，未实施。依据[用户故事重梳](work-journey-stories.md)及当前源码接线制定；本轮不修改应用代码。阶段顺序是建议，不将计划完成等同于应用能力完成。

## 1. 改造策略

按完整用户操作分阶段打通，不先重构全部领域对象，也不继续只改页面摆放。先让已有两条真实方法能在工作项内明确执行和交接，再补齐没有方法时的开始路径，以及局部改进后的正式续做。最后统一查找与阅读入口。

保留 Work、Definition、Run、NodeResult、WorkItem 的现有职责；保留画布与 Agent 共同编辑、固定运行快照、试验比较、共享检查器、持久等待与恢复、显式结项。不迁移所有运行到工作项目录，不复制两套成果，不增加成果中心、自动业务调度器或跨流水线编排平台。

工作项和结果保留两种关系：运行可以为某工作项执行；某成果可以被明确选作输入、留存材料或完成依据。前者不意味着所有输出被认可，后者不改变成果原来的产生位置。来源引用应独立于目标业务身份，不能因为使用某成果就把新运行静默归到源工作项。

## 2. 分阶段交付

### 第一阶段：把“推进”变成明确的本次执行

**用户获得什么：**在工作项内看见并选择本次方法、版本和输入，启动后知道真正执行了什么。

- 以当前已经存在的工作项和方法为起点；先不要求用户重建数据。
- 当前方法可作可见默认值，支持本次更换；“修改工作项方法”不再是换方法运行必须先完成的独立步骤。
- 累计材料与本次输入分开。显示可选材料、已选范围和内容；初次合理预选允许修改，不能静默加入新材料。
- 启动前校验所选版本和输入；失败保留选择，不能留下“方法已换但运行失败”的误导状态。
- 运行记录保存本次准确输入与版本；明确区分试验和正式执行。未决运行仍走停止、事件或恢复，不改变既有并发边界。

**最小实现范围：**WorkItemDetail 的启动入口、items action/launch、共享启动参数与固定输入构造。复用已有材料浏览、方法选择和运行检查；不搭建通用启动向导框架。

**关键接线：**不仅过滤 Run.inputs，也检查 Agent 获取的 workItem.materials 上下文。选择 A/C 时不能仍从旁路把 B 交给模型；业务目标等必要上下文继续明确提供。

**验收：**工作项有 A/B/C，选 A/C 与方法 B，实际运行和 Agent 输入只有指定材料；运行中补 D、修改方法不影响本轮。旧工作项仍可打开和执行，独立试运行保持可用。

### 第二阶段：让成果直接成为下一次处理的输入

**用户获得什么：**在成果上选择“用于下一次处理”，指定目标方法、补充材料后启动，不必先把输出复制成证据。

- 使用第一阶段的同一执行准备入口，成果选择作为预填输入；用户能够检查来源、版本和实际内容。
- 明确选择输出端口及必要的输出项，不把某节点所有端口的输出无区别摊平成一组输入。
- 保留输出值类型和实际来源；不要求复制内部 ID，也不以序列化文本材料替代结构化交接。
- 本轮优先完成同一工作项内跨方法的正式运行；独立调用继续支持。不同工作项使用同一成果的完整选择界面后续安排，不把跨项市场或搜索系统作为前提。
- 报告和材料都可成为输入，是否适合由目标输入契约决定；不能默认报告等价于原始材料。不兼容时明确报出缺口，保留选择。

**最小实现范围：**成果使用动作、输入来源引用与解析、正式启动接线。引用足够定位 work/run/result/port/item，服务端从真实源解析并冻结本次值；具体字段复用现有记录，不新建通用制品存储。源运行仍保留原来的业务归属，目标工作项由本次动作明确指定。

**现有约束：**previewResults 目前只读单个 Work，且合并所有输出；来源推导与去重也以现有上下文为前提。需要明确修改这一边界，不能只在前端传一个跨方法 resultId 或直接放开所有去重检查。

**验收：**CVE 材料收集的结构化材料与业务范围进入影响分析；新 Run 可追溯原成果，并能确认输入中没有误选报告、重复版本或无关材料。两条运行属于同一业务事项，旧成果不改写，业务仍可未结项。

### 第三阶段：从目标开始，而不是先有一条流水线

**用户获得什么：**没有现成方法也能开始一件事，在相同上下文中请 Agent 形成做法，检查后执行。

- 工作项创建保存目标、已有材料与已知完成要求；方法允许稍后选择或生成。业务编号可自动生成，外部编号可填写。
- 复用已有 Agent 生成和画布编辑能力，传入本次业务目标与明确材料；返回时保留工作项上下文，不重新粘贴。
- 无运行时先呈现目标、材料与开始处理入口；有成果后进入适合当前任务的阅读和处理状态。
- 完成条件可逐步明确，但更改条件定义不能沿用已不成立的确认；已结项仍需按既有规则重开。历史运行和历史结项依据不改写。
- 方法区直接调用与局部试验不强制创建工作项；采用方法、试验输入与业务材料不混为同一份持久数据。

**最小实现范围：**创建表单、WorkItem 的可选方法与条件编辑合同、Assistant 上下文接线、App 返回状态。旧数据的 workflowId 继续解释为现有选择，不删除旧关联或重写历史。

**验收：**无方法创建工作项→基于真实目标形成非固定示例做法→检查并修改→明确输入→正式执行。生成失败仍能保存事情与材料；另一个工作项复用方法时不会带入第一项的业务材料。

### 第四阶段：把局部改进接回正式工作

**用户获得什么：**从问题成果做小范围试验，选取可用旧新结果，继续后续处理，而不是重跑已完成部分或永远停留在预览。

- 保留现有候选、同输入比较、独立采用方法和保留结果。
- 第二阶段已覆盖“成果作为另一条完整方法的输入”；本阶段专门处理同一方法内从所选成果继续后续步骤。
- 实施前写清：后续执行范围、被选输出如何接入、还缺哪些依赖、成功步骤是否执行、哪些正式进展允许记录，以及运行结束表示什么。
- 现有 Run.scope 仅有 full／单节点，业务写入受 full/commit 约束；不能把局部 preview 改名为 commit，或把未执行节点填成已完成。
- 原型只围绕明确选择的后续步骤及依赖补齐此能力；不引入任意断点恢复、隐式结果缓存或自动挑选历史结果。

**最小实现范围：**续做输入与范围合同、运行器相应语义、业务进展校验、共用检查器中的实际范围。具体采用范围扩展还是固定后续定义，须以最小实例验证后选定；本计划不预设昂贵执行模型。

**验收：**两条旧成果加一条候选成果继续汇总，只用所选三条，分类步骤不重跑；正式记录归属当前工作项且体现真实范围，试验仍不写业务进展。动态展开、等待与中断恢复按涉及范围回归。

本阶段为必要闭环，不以第二阶段跨方法跑通就标记全部用户故事完成；执行语义未定前不先给 UI 放一个看似可用的“正式续做”按钮。

### 第五阶段：统一查找、阅读与业务完成路径

**用户获得什么：**在业务、方法、运行、成果之间切换时，清楚自己正在看什么，并能完成事情。

- 工作项详情看这件事的目标、进展、明确使用的材料与成果、跨方法执行历史；不把每个中间输出自动提升为业务认可的成果。
- 方法的运行记录以运行为行，工作项作为关联列、筛选或可选分组；成果视图以具体输出为主体。不再强制无工作项的执行伪装成工作项行。
- 成果采用内容名称，节点保留动作名称；显示真实派生来源。默认呈现可阅读内容，按需进入已有共享过程检查器。
- 相同 Run 与成果使用同一份数据和检查组件；保留筛选、选择、阅读位置和明确返回，不补重复面包屑。
- 核对完成条件与真实成果依据，确认结项；业务缺口、运行失败、真实等待保持不同状态。

每个前序阶段都须完成其必要页面交互，不能把可用性推迟到本阶段；这里完成整体一致性收口。

**验收：**两个宽度下走通两条完整故事；独立运行、部分结果、失败、无方法、等待均可理解。测量实际用户动作，比较切换仍保留既有性能收益。

## 3. 依赖与实施批次

```text
明确本次执行 → 成果跨方法交接 → 从目标形成做法 → 局部改进后正式续做 → 整体收口
```

第一、二阶段优先组成可独立验收的第一批：利用现有真实 CVE 方法，解决用户眼前无法指定和交接的问题；不先改执行调度核心。

第三阶段恢复原始产品的开始方式；第四阶段恢复“改进后继续完成事情”的闭环；第五阶段完成整体导航与呈现。避免把全部前端先换一遍，再发现后端无法支撑。

## 4. 验证与兼容要求

- 实施前明确每批最小输入、输出、错误和具体例子，同步调用双方、共享类型与就近 AGENTS。
- 旧运行、来源与结项历史只读保留；新增字段优先兼容旧记录，不清空真实数据或改写历史快照。旧 API 调用的默认行为须明确保留或迁移，不凭新页面推断旧调用者已变更。
- 先用隔离 fixture 验证精确输入、来源、不重复处理、preview/commit 和历史不变；跨模块使用真实 HTTP/runtime 联测。
- 再用本地 Playwright 走完整路径并查看两尺寸截图；模块通过不等于产品路线通过。
- 需要真实模型验证的路线单独记录模型、输入和实际输出；真实 CVE 因仓库不可达仍可未完成，不能为验收编造业务成功。
- 每批记录验收证据，旧视觉 track 的通过与本次文档整理完成都不能计为新功能已验收。

## 5. 本轮交付边界

本轮是改动路径规划，不修改代码，不触发模型、业务运行或数据迁移。后续按批次建立实施任务；首先交付“选择方法与输入→正式运行→选成果→另一方法继续”的可操作路线，再向完整产品闭环扩展。
