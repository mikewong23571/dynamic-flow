# 围绕真实工作持续求解：用户故事重梳

日期：2026-10-22。状态：需求梳理稿，已核对当前代码；不是实现完成或用户已确认所有新交互的声明。本轮仅改文档。原 A–G、H1–H11、T1–T8、L1–L5 保留为回归依据；下文用“故事 1”等称呼，不建立另一套缩写体系。

## 1. 产品要帮助用户完成什么

用户带着真实目标和材料开始；Agent 协助形成可理解的做法；程序按做法执行；用户检查实际结果，针对局部问题试验并修改，保留可用成果，继续完成事情。需要跨时间推进时，工作项保留业务身份、材料、进展与完成依据。

核心价值仍是理解、试验、排查、修改并继续工作。不能退化成“先建好流水线，再填表启动”的工具，也不能把工作项做成只有状态和记录的任务清单。主要角色是独立完成工作的用户，同一个人可以提出目标、编辑做法、检查结果和确认完成；不预设额外管理员或审批角色。

### 保持的原则

- 用户无需写代码、手工拼 JSON、复制内部 ID 或请开发者改数据，便能完成核心路线。
- 画布与 Assistant 修改同一份有限 IR；实际执行遵循它。原始设计的任意 JS 分析方案已被替代，不在本轮恢复。
- 人明确选择要采用的方法、要使用的成果和下一次输入；程序执行已定义的步骤，不要求人在每个节点结束后重新调度。
- 采用做法、保留成果、用于下一次输入、确认为完成依据是不同意图。无需强制做成四个独立页面或四次连续点击。
- 历史运行固定输入和方法版本；新材料不倒灌旧运行，试验不冒充正式业务进展，运行结束不自动结项。
- 页面通过真实内容、状态和操作表达关系，不用说明段落掩盖缺失操作。不为梳理故事增加平台、通用状态机或自动业务调度。

## 2. 用户需要理解的最少关系

| 概念 | 用户为什么需要它 | 边界 |
| --- | --- | --- |
| 工作项 | 持续处理同一件有目标的事情 | 可经历多次运行和不同方法，不等于某条流水线的实例 |
| 流水线／处理方法 | 理解、调整和复用如何处理 | 可以为当前事情生成，也可以选已有方法；不能要求所有人先去方法库建好 |
| 运行 | 知道这一次究竟做了什么 | 固定方法版本、输入、结果和执行状态；可以是试验或正式处理 |
| 成果 | 阅读、使用和追溯处理所得 | 来自某次运行；可作为后续输入，不自动成为已确认的事实或完成依据 |

工作项与流水线通过运行发生联系。现有 workflowId 是当前方法选择，不应被解释为业务永远归属于此方法。工作项可以记住方法选择，不能让用户在启动时看不到它。

同一业务目标需要多种处理方法时，可继续同一工作项；不同目标可以独立建项并引用成果。成果交接不要求业务身份相同，但本轮优先梳理同一工作项内的连续路线，跨工作项成果交接不作为首要实施前提。

材料有两种用途，不能混同：工作项积累的材料供持续追踪和判断；本次输入是明确选来参与本次处理的那部分材料或成果。下一轮知道了什么，取决于它明确收到什么，不是隐式读到所有历史或“记住上次对话”。

## 3. 按用户工作顺序组织故事

### 故事 1：带着目标和已有材料开始

作为用户，我希望先说明想解决什么、提供手头材料，以便开始处理真实事情，而不必先理解内部对象和准备完整流程。

- 触发：只有目标与线索，或者已经知道可用的方法。
- 操作与结果：建立可持续追踪的工作上下文，保存目标、已有材料和已知完成要求；已选方法可带入，未知方法进入故事 2。
- 验收：从全局入口开始时，没有现成方法也能保存这件事；从某条方法进入时明确显示预选方法；不默认以列表第一条代替用户选择。失败保留输入，不偷偷启动模型或运行。
- 建议取舍：编号可自动生成，外部编号选填；完成条件允许逐步明确，但未明确条件时不能直接结项。它们是本轮建议，当前创建仍要求编号、目标、方法和至少一条条件，修改这些约束须同步服务端合同。

### 故事 2：得到并理解当前做法

作为用户，我希望 Agent 根据这件事的目标和材料形成做法，或选择一个已有方法，以便知道准备怎样处理并能调整。

- 触发：还没有方法，或已有方法不适合本次目标。
- 操作与结果：在当前事情的上下文中生成或选择方法，画布显示步骤、依赖、输入与预期输出；用户可手动或通过 Assistant 修改同一份定义。
- 验收：客户反馈与漏洞调查应形成对应目标的做法；用户能指出材料入口、逐项处理与汇总位置。生成失败如实反馈；返回工作项不丢目标和材料，不要求重新粘贴。已有草稿不被静默覆盖。
- 复用边界：修改共用方法影响它的后续使用，应可识别；本轮不设计新的模板发布或方法分叉体系。

### 故事 3：明确这一次怎样处理，再启动

作为用户，我希望在执行前看见本次方法、版本和输入范围，以便知道点下按钮后究竟会发生什么。

- 触发：准备首次处理，或补材料后重新处理。
- 操作与结果：明确选择方法，选择或确认本次材料／成果；能检查内容和来源，再启动一条归属于当前工作项的新运行。合理默认可减少点击，不强制每次弹完整向导，但必须可见、可改。
- 验收：工作项有 A、B、C 三份材料，本次选 A、C，则实际输入只有 A、C；运行中新增 D 或修改方法不改变本轮。缺输入、版本不可运行或输入不匹配时，指出问题并保留选择。
- 边界：正式启动与单节点试验要可区分；存在未决运行时提供处理当前运行的动作，不悄悄再启动一轮。

### 故事 4：掌握进度并处理失败

作为用户，我希望看见实际在处理什么、已得到哪些内容，并能停止或排查失败，以便及时干预。

- 触发：运行中、部分结果已产生、失败或中断。
- 操作与结果：查看当前环节、实例、输入输出和错误；停止有实际反馈；必要时只重试失败部分，保留成功结果。
- 验收：取消不能显示成全部成功；依赖失败输入的后续环节不能伪造结果。重试产生的记录与旧结果可区分。节点执行状态、Agent 报告的业务阻碍、真实等待分别呈现。

### 故事 5：看懂成果并判断能否使用

作为用户，我希望直接阅读成果，并能查看它的范围、来源和处理过程，以便决定是否使用。

- 触发：运行产出报告、数据集合或部分结果。
- 操作与结果：以内容名称呈现成果；按需追溯到固定运行、输入与环节，返回后保留阅读位置。支持复制和结构化内容检查。
- 验收：“漏洞调查材料”与“调查报告”能区分，能知道报告基于哪份材料生成；不把“形成材料调查结果”等节点动作直接当作唯一成果名称。未决项与不完整结果不能显示成已证实结论。
- 边界：报告可能是独立生成的派生输出，不必强行与结构化材料合并成两个显示模式；来源由真实记录表达，不能靠字段名猜关系。中间结果仍可检查，但不全部挤入最终成果列表。

### 故事 6：针对具体问题试验和改进

作为用户，我希望从不满意的结果进入对应步骤，用少量真实输入试验改法，以便不必重跑整件事情。

- 触发：分类错误、缺失依据、输出结构不合用等具体问题。
- 操作与结果：定位对应方法版本与节点，形成候选，选择样本，对比同输入的当前与候选结果；决定采用方法、保留某些成果，或继续调整。
- 验收：旧样本来源、候选变化与比较有效性可查；切换页面保留选择；仅布局变化不使比较过期。采用做法不自动确认试验成果，保留成果也不自动采用做法。试验不写正式工作项进展。

### 故事 7：用已有成果继续完成剩余工作

作为用户，我希望选取已经可用的成果，明确下一步处理方式，以便沿用已完成的工作，而不是重新处理全部材料。

- 触发：部分成果已可用，下一步可能沿同一方法继续，也可能使用另一种方法。
- 操作与结果：从成果选择进入后续处理，保留工作项身份与所选成果来源；明确目标处理步骤／方法及输入，补充必要材料，启动新的运行。试验与正式处理的影响在执行前明确。
- 验收：旧运行两条成果与候选的一条成果被选为汇总输入，实际只用这三条；同一来源存在两个版本时由用户明确选择，不静默混用或覆盖。切换方法后仍能查到原成果与旧运行，不要求复制 ID 或手动拼交接 JSON。
- 边界：一般选取成果作为输入，不应被迫先将它声明为“已确认的证据”。选择输入不代表任意两个方法的输入契约天然兼容；不兼容时指出缺什么，允许明确准备材料或调整方法，不建设通用自动转换平台。
- 待设计边界：现有局部续做是 preview，正式推进是 full/commit。本故事要求接通正式业务路线，但不能简单把 preview 改成 commit。需明确哪些后续步骤真实执行、业务进展如何记录、未执行部分如何呈现；旧运行不能被标为新一轮全部完成。

### 故事 8：等待信息到达，继续合适的执行

作为用户，我希望知道在等什么，并在信息到达后继续工作，以便跨时间处理而不丢失已完成内容。

- 触发：流程配置的等待、执行被中断，或报告指出材料不足。
- 操作与结果：真正等待时按匹配事件／到期继续同一次运行；中断按明确恢复动作保留已完成实例；仅有业务缺口时补充材料，按需要发起新运行。
- 验收：重启后等待仍存在，已完成节点不重复执行；停止后旧消息不唤醒；补充工作项材料不改写旧运行输入。报告写“缺源码”不等于执行器已进入等待。

### 故事 9：确认业务完成，必要时重新打开

作为用户，我希望按目标及完成条件核对依据，以便判断事情是否完成，而不是被一次成功运行误导。

- 触发：已有足够成果，或新证据推翻此前结论。
- 操作与结果：逐项确认完成条件和对应依据，明确结项；新信息到来时带原因重开，保留此前判断。
- 验收：运行成功而证据不足时仍未结项；不能用节点完成百分比代替完成条件；引用具体成果保留来源，试验输出不能自动满足条件。重开不抹去历史结项记录。

### 故事 10：回来继续，复用方法，观察多件事

作为用户，我希望能找回正在处理的事情和可复用的方法，以便持续工作并减少重复准备。

- 触发：重新打开应用、开始另一件事，或需要总览多项进展。
- 操作与结果：工作项按业务状态查找；方法库按方法查找、重命名或归档；复用方法处理新材料时保持业务材料独立。无需持续追踪的一次直接调用或方法试验，不强制先建工作项。
- 验收：两个工作项使用同一方法但输入不串；历史、草稿与已保存成果可恢复；外部 HTTP 与页面看到一致业务状态。模型设置失败、服务中断和读取错误如实反馈。

## 4. 页面由这些任务决定

这是页面职责建议，不是本轮已实施的导航结构；具体布局留待设计。

| 用户任务 | 页面应承担的职责 |
| --- | --- |
| 持续完成一件事 | 工作项承载目标、材料、成果、执行进展和下一次处理入口；未运行时首先呈现开始工作的动作，而非空的成果检查器 |
| 理解或修改做法 | 方法工作区提供画布、配置、Assistant 和试验；来自工作项时保留其上下文及返回入口 |
| 查看一个方法的执行情况 | 以运行记录为主体，工作项为关联列、筛选或分组；成果视图按具体输出组织 |
| 阅读和使用内容 | 成果内容优先，提供来源和使用动作；深入过程使用同一个运行检查核心 |

“推进”不能遮蔽实际动作。开始新运行、试验、选成果续做、发送等待事件、中断恢复、确认结项有不同效果，必须从当前状态与动作中辨认。无需用一排全部可见的按钮实现。

## 5. 两个端到端验收场景

### 场景一：漏洞调查，跨方法持续处理

1. 输入“查清漏洞对两个系统的影响”与现有线索；无现成方法也能保留业务事情并形成做法。
2. 选择／生成材料收集方法，确认本次输入，执行并阅读调查材料和派生报告。
3. 选择调查材料，指定业务影响分析，补充两个系统的范围和依赖线索；界面明确显示下一轮将收到什么。
4. 实际分析缺源码时保留待定结论，运行结束但工作项未结项；不凭报告文字自动等待或调度。
5. 补齐线索，明确新一轮输入；先前版本、输入与待定结果保持可查，再按完成依据决定是否结项。

关键反例：在步骤 3 只点现有“推进工作项”，当前实现会再次执行已绑定方法，并使用全部工作项材料，不会自动得到上述交接。此路径尚未验收通过。

### 场景二：客户反馈，局部改进后沿用成果

1. 提供三条反馈和“分类并形成有引用的建议”的目标，由 Agent 形成做法。
2. 检查混合反馈的分类，发现具体问题，选两条输入试验候选；两侧同输入比较。
3. 即使不采用候选，也可保留它的一条可用成果；同时选两条旧成果。
4. 确认以这三条成果继续汇总，实际不重跑分类、不重复同一输入的多个版本；如进入正式工作项处理，业务记录真实反映本轮执行范围。
5. 阅读报告并追溯三条来源。另一个工作项可复用已采用方法处理新材料，输入与成果独立。

关键反例：方法区现有“用所选结果续做”可验证局部输入，但关联工作项时属 preview；不能把它通过当成正式业务续做已经贯通。
