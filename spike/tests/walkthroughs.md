## T1：目标 → 做法 → 报告

1. Workspace 保留输入；createWork 检查目标和三条已确认材料，保存 W1。缺项时没有丢输入的路径。
2. requestEdit 取 W1 的真实材料与目标，请 Pi 生成；proposeFlow 调用 saveDraft，得到 d1；未保存成功就不显示修改完成。
3. 后端推送 W1，画布和配置同时看到 d1。节点名称/输入/输出来自定义，不是另写一份静态图。
4. 用户明确选择 d1 和 F01/F02/F03；start 保存输入快照，后台逐项分类后汇总，结果记录到 r1。
5. report 读取 r1 的声明输出；用户能查看来源并复制正文。尚未完成/失败时不返回完整成功标签。

推演结论：生成、编辑和执行指向同一个定义 ID；界面没有要求用户写代码。剩余实证：真实模型能生成可用定义，真实报告质量符合要求，复制与长内容可用。

## T2：手工修改与条件分流

1. 插入 select-fields，明确重接分类与汇总之间连线，saveDraft 产生 d2；删除节点后清理关联边，残留输出引用就地提示。
2. 运行检查在新定义上完成；拓扑与端口输入来自该定义，因此拖线改变实际数据路径。
3. 对 d3 只提供 F03，Branch 的 match=[]、rest=[F03]；match 下游 each 直接完成且无模型调用。
4. merge 等待两个上游都完成，拿到 [] 和处理后的 F03，输出可送入报告；空数组不是“上游没返回”。
5. 缺必需配置/回连时保留草稿但不创建 Run；修正后才运行。移动位置只保存 view，不产生新定义。

推演结论：空分支不需要特殊调度平台；使用集合与明确端口即可说明结束条件。剩余实证：画布编辑事件与实际数据依赖一致、错误位置可理解。

## T3：对话修改与同输入试验

1. 采用 d1 后，从 F01 的结果选中 classify；发送修改时固定 target=classify、expectedDraftId=d1、样本上下文。
2. 模型工具只修改请求范围，saveDraft 产生 d2，adoptedId 仍是 d1；配置面板同步显示实际改动。
3. 选择 F01/F03，compare 固定两版与相同输入内容，先运行 d1 再运行 d2；F02 不进入任何一侧的输入。
4. 逐项结果按 sampleId 对齐；输入契约不兼容时提前提示，不自动运行不同材料来假装可比较。
5. 用户查看 F01 是否修复、F03 是否被误伤。基线失败也如实展示，允许看候选；停止整个比较则不会启动下一侧。

推演结论：无需第三套试验会话或评测框架。剩余实证：Pi 实际修改、相同样本进入两次调用、流式及工具卡片可用。

## T4：编辑、请求和运行交错

1. 模型请求捕获 d1 后，用户手工保存 d2；旧工具再保存时 expectedDraftId 不匹配，files.change 不提交旧提案。
2. 切换画布选择只改变界面 selectedNodeId，不改变旧请求目标；不相关节点不被覆盖。
3. 已启动 r1 仍持有 d1 和输入快照；后台不重新读取当前草稿作执行依据。
4. 比较固定候选 d2，但用户保存 d3；readComparison 发现 candidateId != draftId，显示过期。
5. 旧运行迟到的 completed 只改变运行状态，不能改变上述版本比较；仅布局或列表排序变化不使比较过期。

推演结论：需要的只是版本起点比对与冻结输入，不需要协作冲突合并。剩余实证：异步真实交错时保存和 UI 状态仍一致。

## T5：采用做法与保留结果

1. adopt(d2) 只改 adoptedId；没有把比较两边全部结果加入 keptResultIds。
2. 另一条路径只 keep(r2.F01)，adoptedId 保持原值；discard 只恢复草稿指针，不删除 r2。
3. 从保留结果明确选择 r2.F01、r1.F02、r1.F03，continueWithResults 返回输入预览；用户确认后发起 report 单节点 r3。
4. r3 固定的值与来源就是这三条，不会读取所有保留结果或按“最新版本”重新选择。
5. 同时选中 r1.F01/r2.F01 时先提示同材料冲突，用户选定一个才继续。输入不符合报告要求也先提示。

推演结论：采用与保留没有隐藏耦合；续做是明确输入的新运行。剩余实证：混合来源保存正确，输入预览与实际报告一致。

## T6：停止和失败

1. stop 在 files.change 中将运行置 stopping；活跃模型调用收到 abort；execute 在每次调用前后检查停止。
2. 若停止先提交而成功响应后到，响应不作为成功结果；后续节点不执行。若完成先提交，stop 返回原 completed，不改写历史。
3. 另一运行 F02 失败时记录失败输入，F01 与其它独立项结果仍保留；汇总节点 blocked。
4. retry 从失败记录取原输入，用用户明确选择的定义发起单节点新 Run，成功后由用户决定如何续做。

推演结论：本地取消与完成顺序有明确结果；不承诺外部服务立即停止计算。剩余实证：SDK abort、迟到回调、失败注入、调用次数和状态保存。

## T7：复用、保存、刷新与重启

1. addMaterials 追加 F04；用户选择采用版 d2 与 F04，start 只冻结这一条；旧输入/报告不被改写。
2. files.change 成功后 UI 才显示已保存；新定义先写完，工作索引后更新。索引写失败时仍能打开旧工作。
3. 页面刷新只是 read/subscribe，仍存活的后端运行继续；SSE 重连收到最新完整状态，无须回放漏掉的事件。
4. 后端重启时，已无本地句柄的 queued/running/stopping Run 与 Comparison 改为 interrupted；完成结果仍可查看，不自动续跑。
5. 保存的定义、候选、采用版、视图、结果、消息和比较关系恢复，能继续明确发起下一次操作。

推演结论：正常重开与执行中断有不同路径；本地文件足以说明首版保存需求。剩余实证：真实磁盘写入失败、重启和连接重建。

## T8：完整工作区体验

沿 T1/T3/T5 操作时，画布、所选节点、结果、对话与比较共用同一工作上下文。伪代码已经为未保存、冲突、过期、停止中、失败、部分完成、断线和中断指定反馈位置。

只能得出“需要哪些状态与动作已经说明”，**不能推演出页面有品味或用户觉得好用**。必须在代表性真实页面研究和统一控件、密度、字体与色彩，并在两个窗口尺寸下实际操作、截图、获得用户反馈。

## 当前判断

19 个故事均有负责模块、可追踪接口、测试场景与验收路线。第 1 轮发现的断点已在最终伪代码中给出处理分支；这仍是可供实现验证的设计判断。真实 SDK 兼容性、模型质量、取消时序、文件故障和视觉体验保留为明确待验收项。
